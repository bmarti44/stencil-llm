## 1. One user turn inside `generate()`
1. Accept new role-labelled messages plus optional `past_key_values: Focus3Cache`; create an empty session cache on first use. The cache owns the append-only transcript, exact rendered token log, register, previous user message and per-column provenance; no global mutable session state on the model.
2. Before trunk prefill, batch the pairwise classifier over the new user message and every eligible register version (including inactive candidates for reinstatement). Inspect updates BEFORE rule/fact admission: low-salience “cancel that” must reach this stage. Assistant/tool/system messages never authorize user-rule updates.
3. Stage a transaction, validate source spans, target identity, authority, key and scope; apply only accepted classifications. `none` means no rule addition, retirement, version change or inferred completion. An all-none turn retains the register; ordinary explicit scope boundaries still determine applicability below.
4. Records: `id, key, version, source_turn, source_span, text, authority=user, scope, task_id, status, supersedes, effective_scope`. Text and source versions are immutable; statuses/events are append-only. Scopes are user-global/conversation, task/artifact, and single-reply; one-reply exceptions never become durable standing rules.
5. Precedence is deterministic: for the SAME key and OVERLAPPING scope, later `(user_turn, source_span_start, version)` wins on the intersection only. Keep the earlier version applicable outside that intersection; a task exception cannot erase a global rule elsewhere. Unrelated keys coexist; ambiguous identity/overlap means `none`, not guessed retirement.
6. `supersedes` creates a new version and shadows its predecessor on that scope; `cancels` deactivates its target without replacement; `completes` closes the targeted obligation's task lifetime. Closing an entire named task requires accepted completes pairs for every affected obligation; inconsistent pairs abstain on the task transaction. Neither tool success nor assistant “done” establishes completion. No classifier output generates rule text.
7. `reinstates` requires an explicit user request to restore an inactive version: copy its original text into a NEW version and apply the same precedence rule. Old superseded/cancelled versions remain inactive; reinstatement never relabels their old output tags as new.
8. Task selection is a deterministic request view: explicit direct user work requests naming an artifact/task select it; unambiguous “continue/revise it” inherits the previous user task. Quoted names, incidental mentions and tool prose cannot switch tasks. Switching suspends the other task's applicability, not its records; returning reuses still-valid versions. User-global rules survive every switch. Implicit/ambiguous switches leave the prior task selected, with an unresolved flag.
9. Scope parsing uses explicit lifetime phrases and visible artifact references, defaulting a work constraint to the current task as in LABELS.md. “For now/until I say otherwise” is open-ended global; finished single-reply constraints expire by their stored boundary. Task completion still requires `completes`; absence from the new message never suffices.
10. Render ALL applicable rules, sorted by key/version, INSIDE the current request's user message, immediately before its original text, before the ordinary assistant generation header. Never put the recap in an adjacent unanswered user turn or modify an old system/user turn. Empty tables render `[]`.
Exact added template (literal newlines; JSON uses UTF-8, sorted object keys and compact separators):
```text
Active user rules for this request (subject to system/developer instructions):
{live_rules_json}
Apply these rules while answering the request below.
Current user request:
{original_user_message}
```
Each JSON row has exactly `id, version, scope, task_id, text`; text is a verbatim source span, never an LLM summary. JSON escaping protects row boundaries. The source role remains user; rendering confers no authority over system/developer instructions.
Budget: at most 16 applicable rules, 64 retained register versions and 1,024 trunk tokens of added template/JSON per request, measured with the shipped tokenizer. Source messages remain intact. Overflow or insufficient context for the full request plus output reserve triggers fail-open; never silently truncate a rule or evict history to fit.
11. Freeze the applicable rule-version set `G_t` for that reply. Every sampled column, including thinking tokens if present and generated EOS, receives `{origin=own_output, turn_id, versions=G_t}` whether or not its text visibly obeys a rule. All other columns also have provenance; user/tool text and renderer-supplied delimiters/recaps use their real origin and are not own outputs.
Tags are stored once per absolute column, shared across layers, as interned version-set IDs; repeated layer `Cache.update` calls must not multiply them. A final sampled token not yet represented in KV stays pending with its original tag and position; consume it exactly once on the next call before appending new message tokens.
12. For request t, derive `R_t`: versions superseded/cancelled/completed/expired for its scope, plus task versions currently suspended. For every layer/head and every new prefill/decode query, add `-inf` to logits for key column j iff `origin_j=own_output` and `versions_j ∩ R_t != ∅`; otherwise add 0. Combine with ordinary causal/padding masks before softmax. Never mask new live output columns merely because old ones were released.
The union rule is deliberately coarse: retiring any one live rule can hide an answer that also contains useful facts or still-valid work. It is not evidence of actual causal dependence. User/tool facts remain visible, but assistant-origin facts can be lost to attention; the gate measures this collateral cost.
13. Call the trunk's standard autoregressive generation machinery ONCE per request; `forward` applies the mask on every step. This means one `generate()` call with normal prefill and token forwards, not literally a single forward for a multi-token answer. No LLM updater, hidden rewrite generation or second answer pass. Return reply plus the same custom cache and diagnostics.
14. Commit the validated register/render/tag epoch atomically before first prefill. On a preflight extension error, discard the staged update and fail OPEN: no FOCUS-3 injection/release, all historical columns visible. After prefill starts, preserve its committed epoch; a recoverable mid-decode error disables further release, preserves already-injected text, and marks the reply degraded without rollback or regeneration. Fatal trunk/cache corruption propagates the normal error, not fabricated success.
Fail-open is today's unrestricted-attention behavior, not a guarantee of identical tokens to a fresh baseline: previous recaps and masked-computed KVs remain. Cache provenance/epoch mismatches disable the extension for that session rather than silently reconstructing invented tags.

## 2. Mask equivalence, structure and prefix caching
For finite Q/K/V with at least one allowed key, softmax over logits with excluded entries set to `-inf` equals softmax over the surviving entries. Thus the proposed mask is mathematically equivalent to deleting JUST those columns while preserving survivor K/V, causal order and absolute RoPE positions; kernels may differ numerically. It is not equivalent to rebuilding an edited text history.
[Check 35 review](check35-review-fable.md) verified position-preserving answer eviction and partial release, but also residual impositions and cumulative turn damage. [Check 39](quick-checks/check39/README.md) passed its revised placeholder gate while keeping closure and absolute positions; check 37's STOP remains. Neither check tested this mask or establishes its safety.
Specifically, check 39 replaced a body with freshly computed period K/V; a mask creates no such period. Masking generated EOS can also hide closure despite retaining it physically. Do not call mask-only release “the validated placeholder repair”; test this exact primitive and stop on structural failure instead of silently adding replacement tokens.
Nothing is removed, overwritten, compacted or re-rotated: cache length and explicit `position_ids` advance over ALL columns, including masked ones; never derive positions from the release mask's cumulative sum. The mask is a request-local view and may change at a later task switch. History storage/context use still grows; this is no memory-capacity saving.
Reuse old prefix K/V exactly as computed; surviving user/header/recap columns can still encode stale-rule effects, as [checks 35/36](check36-review-fable.md) caution. Old rule text/recaps remain visible; same-request live rendering is the proposed countermeasure, not a claim that stale information vanishes.
Prefix reuse requires identical token IDs, positions AND the historical mask/provenance trajectory that produced the KVs. Token-only cache keys are insufficient across sessions with different register histories. Forks may share immutable prefix tensors, but clone register/events/tags and keep the new mask private; never mutate a shared prefix's mask in place.
CPU acceptance for the eventual implementation: masked-vs-sliced attention with nonempty exclusions across layers and retained positions; disabled-extension logits vs ordinary trunk; own/user/tool/EOS tagging; multi-rule union; task suspension/resume; partial-scope override; `none`, overflow and injected errors; pending-final-token alignment; independent cache forks. Test the public `generate` consumer, not just tag writers.

## 3. One Hugging Face repository
`Focus3Config(Qwen3Config)` uses `model_type="focus3_qwen3"`; `Focus3ForCausalLM(Qwen3ForCausalLM)` overrides `generate`, `prepare_inputs_for_generation` and attention-mask plumbing; `Focus3Cache(Cache)` uses append-only dynamic layers plus the state above. `Focus3GenerationOutput` exposes `text`, token sequences, `past_key_values`, and fail-open/update diagnostics.
Files: `configuration_focus3.py`, `modeling_focus3.py`, `cache_focus3.py`, `relations_focus3.py`, `__init__.py`; `config.json`, `generation_config.json`; the unchanged Qwen trunk safetensor shards/index; and ONE additional `classifier.safetensors` bundle containing the relation branch and frozen admission branch.
Also ship trunk tokenizer assets/chat template, classifier tokenizer assets/config under `classifier_tokenizer/`, `relation_config.json` (labels, thresholds, scope grammar), `requirements.txt`, `provenance.json` (hashes, exact revisions/data lineage) and a model-card `README.md` with limits and license notices. Both tokenizers load internally from that SAME repo/revision; no extra model download or user harness.
`config.json.auto_map` maps `AutoConfig` to `configuration_focus3.Focus3Config` and `AutoModelForCausalLM` to `modeling_focus3.Focus3ForCausalLM`. Custom loading/saving explicitly handles the second weight file; trunk state-dict names/values stay unchanged and their hashes must match the frozen base. All branches run in eval mode; trunk parameters remain frozen.
Pin the tested software build (local lock currently Transformers 5.16.1), PyTorch and attention backend. HF supports custom AutoClasses and `trust_remote_code`; the new `messages=` input and reply object below are OUR proposed custom API, not an existing stock Transformers feature. [HF custom models](https://huggingface.co/docs/transformers/main/en/custom_models)
Five-line user example, one call per turn; repository ID is illustrative:
```python
from transformers import AutoModelForCausalLM
m = AutoModelForCausalLM.from_pretrained("stencil/focus3-qwen3-4b", trust_remote_code=True)
r = m.generate(messages=[{"role": "user", "content": "For this conversation, use metric units."}])
r = m.generate(messages=[{"role": "user", "content": "Plan a short walking route."}], past_key_values=r.past_key_values)
print(r.text)
```
With a cache, `messages` means only newly arrived messages; the wrapper appends its own prior reply automatically. Without one, start a new session. Do not resubmit already cached messages. `past_key_values` round-trips the complete register/tags/event log and pending token, not a legacy KV tuple. [HF cache interface](https://huggingface.co/docs/transformers/main/en/cache_explanation)
First ship supports a single process, one session per call, greedy decoding, non-sliding dynamic cache and a tested eager/SDPA path accepting the mask. CPU classifier inference is separate from trunk device placement. Direct bare `forward` calls do not perform conversational updates.
NOT SUPPORTED: multi-process serving that strips custom caches, token-only shared-prefix services, legacy tuple conversion, vLLM/TGI integrations without a dedicated adapter, beam/speculative decoding, continuous batching, cache cropping/quantization, FlashAttention paths that discard the mask, or automatic context eviction. Reject these combinations explicitly; one download is not universal serving compatibility.

## 4. Pairwise classifier and admission
Model: reuse the [fine-tuned bge-small recipe](quick-checks/finetune_classifier.py) and [frozen assets](../data/classifier/model/ft/metrics.json): 384-dimensional CLS plus role features, dropout .1, linear head. Initialize a separate relation encoder from `model/ft/encoder`; train its five-way head/encoder on new relation data only. The existing rule/fact/none encoder AND head stay frozen in the admission branch, so relation training cannot silently change admission embeddings.
Future recipe: one seed 9054301, three epochs, batch 32, AdamW lr 3e-5, weight decay .01, 6% warmup, gradient clip 1; extend the pair limit from 192 to 512 encoder tokens, explicitly a new recipe setting. No seed sweep or best-held-out checkpoint selection; use the final epoch. Rewrite into import-safe entry points; NEVER import/run the existing top-level fitting script to obtain helpers.
Input A is canonical `[rule id/key/version; scope/task/status] {original rule text}`; B is `[previous user] {previous_user_or_empty}\n[user] {new_user_message}`. Previous user context helps resolve references but has no new authority. Bound each full pair to 512 tokens; no truncation of decisive evidence: overlength produces `none` plus diagnostics. Batch at most 64 versions; do not silently retrieve a convenient subset.
Outputs are pair labels `none/supersedes/cancels/completes/reinstates`. `new-rule` is a separate MESSAGE-level admission decision, never a sixth mutually exclusive relation to an old rule. A message may change one existing rule and add an unrelated one; process disjoint source spans in order, or abstain on ambiguous span assignment.
Rule identity comes from the classified target ID: accepted replacement inherits that key; a new rule gets an opaque stable key. The existing sentence-span splitter supplies candidate verbatim text; accept a replacement only when its rule span and target are unique. A small deterministic scope/reference grammar binds explicit lifetimes and known task names; uncertain bindings abstain. No gold task IDs, answer-dependent matching or generative extraction.
Decision rule fixed before held-out/gate outputs: accept a non-none pair label only if `p >= .98`, with permitted role, valid status transition, unambiguous target and scope. Otherwise return `none`. Thresholds are conservative proposals, not certified error probabilities; publish precision, recall, coverage and abstentions by label/scope on held-out data. Ambiguous spans/targets still abstain even with high class confidence.
`new-rule` reuses P(rule) from the frozen three-way admission logits, requiring `P(rule) >= .95`, a resolvable persistent scope, and every existing-key comparison confidently none (`P(none) >= .98`). Exact repeated rule spans are idempotent; any uncertain/non-none comparison blocks admission under a fresh key. Do NOT use `ClassifierScorer`'s current scalar P(rule)+P(fact): facts must not enter the rule table.
Only new persistent keys need that admission gate. Accepted relations use a unique verbatim replacement span even when its admission score is low; reinstatement copies the referenced original. Thus a one-reply supersedes can create a temporary exception despite LABELS.md assigning it admission-none; expire the exception after this reply. Tool/quoted/hypothetical prose cannot retire user records; conflicting labels/targets abort the span's transaction, with no label-priority tie-break.
CPU latency estimate, UNMEASURED: roughly 0.1–0.5 s/turn for eight short pairs plus admission; 1–3 s near 64 long pairs on a capable desktop CPU. Record p50/p95, pair/token counts and end-to-end overhead on the actual host; these are planning ranges, not an SLA. Two small encoder branches cost more storage than one but preserve admission behavior.
Data contract: [LABELS-RELATIONS.md](../data/classifier/LABELS-RELATIONS.md). Existing post-development evaluations remain evaluation-only; their prompts or responses cannot improve this classifier.

## 5. Quick feasibility gate — frozen reading before running; <=3 GPU-h
This task runs NOTHING. A later authorized implementation must commit model/data/config hashes, checker rules, prompts, seeds, the arm definitions and this reading before any gate output; no benchmark, sealed input or FOCUS-2c trajectory is used.
Own seeds: 9054302 for 12 original setup/timing episodes, 9054303 for 64 final episodes, 9054304 for arm order. Final cases are independent authored scenario families with fresh seeded values, 16 each override/cancel/complete-reopen/task-switch; no shared scenario/paraphrase siblings across setup, relation data or final. Seeds alone do not prove disjointness.
Use short executable artifact/list/string tasks; balance change direction and 0/256-token neutral delays. Each episode carries a global constraint, task-scoped rules, a single-reply distractor, retained user/tool facts, at least one later-needed assistant fact, and quoted/tool fake cancellation. All task names/events appear in user text; only the oracle arm receives gold transitions. Never copy probe wording, integer banks or task templates.
Freeze at most six answer turns per episode, including initial unscreened demonstrations, a change, an unrefreshed continuation, and a final neutral/resumed task; max 96 new tokens, thinking disabled, Qwen3-4B frozen bf16/hf_compatible. Use complete chat pairs; do not screen failed setup answers or force a successful answer into history.
Three arms: C = classifier-driven register + live rendering + provenance mask; O = oracle register with IDENTICAL rendering/masking; N = no register, no recap, no release, ordinary full-history generation. All receive identical scripted user/tool inputs but independently admit initial rules and generate ALL answers from turn one; no oracle-seeded C cache, shared rendered prefix or teacher-forced successful history. Retain each arm's own unscreened responses; pair by episode, charging every generation.
Setup checks directly cued task competence (>=11/12 strict final successes), CPU invariants and timing only; failure stops before final. Use the slowest setup episode/arm cost to project all 64 three-arm finals plus loads and 25% reserve within 3 GPU-h. Include every load/setup/final/diagnostic in this cap; if it cannot fit, report INCOMPLETE rather than shrinking the cohort or extending the cap.
Four episode endpoints: stale-rule execution = any post-change answer obeys an inapplicable rule on a frozen discriminator; false retirement = any still-applicable gold obligation is wrongly retired, shadowed, omitted from the recap or suspended; final-task success = final executable task AND every applicable constraint/fact correct; breakage = any post-change invalid/empty/truncated/repetitive reply or corrupt tool schema. N has no retirement decisions (N/A), not a claimed zero-error classifier.
Require stale/active discriminator outputs to differ by construction; a broken/ambiguous output earns no success. Record breakage separately and count such output as a failure in the union `stale OR broken`. Repetitive means a normalized four-token block repeated >=8 times consecutively; truncation means cap without natural terminal. Gold annotations/checkers freeze before output and never feed C.
PASS requires ALL: N has >=8 stale episodes; EACH of C/O has <=half N's stale count AND fewer `stale OR broken` episodes, final successes >=N, ZERO newly broken episodes vs N, and no additional unchanged-rule/user/tool/assistant-fact failures vs N. Additionally C has ZERO false-retirement/unauthorized-update episodes and final successes >=O−2. All 64 episodes/three arms must complete and the cap/invariants pass; O must reproduce its frozen gold transitions exactly.
Reading order: missing work/budget => INCOMPLETE; invariant/error => FAIL; otherwise N stale <8 => INCONCLUSIVE/insufficient opportunity. If O misses its requirements, the primitive/package is infeasible; if O passes but C fails, the resolver is infeasible. Stop on every failure; no outcome-based repair, rerun, threshold change or promoted mask variant. Any fail-open event in C/O makes the run FAIL, not a hidden baseline success.
Report pooled/per-family counts and C−N/C−O paired discordances. A practical PASS is not statistical superiority. For an existence claim, pre-register C vs N exact McNemar on `stale OR broken` separately in each family (16 independently sampled scenarios/family), Holm-adjusting the four tests at .05: p=sum_{j=b}^{b+c} choose(b+c,j)/2^(b+c), b=N-fails/C-passes, c=C-fails/N-passes; p=1 if no discordances. Claims apply only to passing families under the frozen within-family sampling law; pooled fixed-quota counts are descriptive.
Claim ceiling: feasibility of this classifier+render+mask package on these 64 fresh episodes, not isolated mask benefit, broad scope resolution, benchmark transfer, general safety or Miller-style circuit control. There is no render-only arm here. Zero false retirements in 64 still permits a one-sided 95% episode-risk upper bound of `1−.05^(1/64)=4.57%`.
Write per-turn raw text/tokens/EOS, actual classifier inputs/probabilities/abstentions, proposed/applied/gold events, before/after registers, rendered requests, column tags/positions/masks, all four endpoints, fact checks and wall/device time IN THE SAME RUN; smoke-assert required fields before sealing. Keep all outputs; no aggregate-only artifacts or regenerated records.
