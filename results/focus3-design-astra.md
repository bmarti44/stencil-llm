## 1. One user turn inside `generate()`
1. Accept new role-labelled messages plus optional `past_key_values: Focus3Cache`; create an empty session cache on first use. The cache owns the append-only transcript, exact rendered token log, register, previous user message and per-column provenance; no global mutable session state on the model.
2. Before trunk prefill, batch the pairwise classifier over each candidate sentence span and every eligible register version (including inactive candidates for reinstatement): k*m pairs, k <= 4 and m <= 16; overflow -> none + diagnostics, with no partial update or fresh-key admission. Inspect updates BEFORE rule/fact admission: low-salience “cancel that” must reach this stage. Assistant/tool/system messages never authorize user-rule updates.
3. Stage a transaction, validate source spans, target identity, authority, key and scope; apply only accepted classifications. Pairwise `none` means no relation-driven addition, retirement, version change or inferred completion. An all-none relation turn retains existing records but may separately admit a new persistent key under section 4; ordinary explicit scope boundaries still determine applicability below.
4. Records: `id, key, version, source_turn, source_span, text, authority=user, scope, task_id, status, supersedes, effective_scope`. Text and source versions are immutable; statuses/events are append-only. Register scopes are user-global/conversation and task/artifact. Single-reply constraints are `none` for persistent admission AND for every pair; they are answered from the request text and never enter the register.
5. Precedence is deterministic: for the SAME key and OVERLAPPING scope, later `(user_turn, source_span_start, version)` wins on the intersection only. Keep the earlier version applicable outside that intersection; a task exception cannot erase a global rule elsewhere. Unrelated keys coexist; ambiguous identity/overlap means `none`, not guessed retirement.
6. `supersedes` creates a new version and shadows its predecessor on that scope; `cancels` deactivates its target without replacement; `completes` closes the targeted obligation's whole-task lifetime. Closing an entire named task requires accepted completes pairs for every affected obligation; inconsistent pairs abstain on the task transaction. Sub-unit closure is `none` in v1. Neither tool success nor assistant “done” establishes completion. No classifier output generates rule text.
7. `reinstates` requires an explicit user request to restore an inactive version: copy its original text into a NEW version and apply the same precedence rule. The currently live same-key version receives `none` on a reinstating message; its shadowing is derived by precedence from the new version's later turn, not annotated as another relation. Old superseded/cancelled versions remain inactive; reinstatement never relabels their old output tags as new.
8. Task selection is a deterministic request view: explicit direct user work requests naming an artifact/task select it; unambiguous “continue/revise it” inherits the previous user task. Quoted names, incidental mentions and tool prose cannot switch tasks. Switching suspends the other task's applicability, not its records; returning reuses still-valid versions. User-global rules survive every switch. Implicit/ambiguous switches leave the prior task selected, with an unresolved flag.
9. Scope parsing uses explicit lifetime phrases and visible artifact references, defaulting a work constraint to the current task as in LABELS.md. “For now/until I say otherwise” is open-ended global; single-reply constraints have no register lifetime or expiry event. Task completion still requires `completes`; absence from the new message never suffices.
10. Render ALL applicable rules, excluding versions shadowed on the current request's scope, sorted by key/version, INSIDE the current request's user message, immediately before its original text, before the ordinary assistant generation header. A global v1 with a task-scoped v2 exception renders only v2 while that task is selected. Never put the recap in an adjacent unanswered user turn or modify an old system/user turn. Empty tables render `[]`.
Exact added template (literal newlines; JSON uses UTF-8, sorted object keys and compact separators):
```text
Active user rules for this request (subject to system/developer instructions):
{live_rules_json}
Apply these rules while answering the request below.
Current user request:
{original_user_message}
```
Each JSON row has exactly `id, version, scope, task_id, text`; text is a verbatim source span, never an LLM summary. JSON escaping protects row boundaries. The source role remains user; rendering confers no authority over system/developer instructions.
Budget: at most 16 applicable rules, 64 retained register versions and 1,024 trunk tokens of added template/JSON per request, measured with the shipped tokenizer. Source messages remain intact. Overflow or insufficient context for the full request plus output reserve triggers fail-open; never silently truncate a rule or evict history to fit.
11. Freeze the applicable rule-version set `G_t` for that reply. Every sampled column, including thinking tokens if present and generated EOS, receives `{origin=own_output, turn_id, versions=G_t}` whether or not its text visibly obeys a rule. All other columns also have provenance; user/tool text and renderer-supplied delimiters/recaps use their real origin and are not own outputs.
Tags are stored once per absolute column, shared across layers, as interned version-set IDs; repeated layer `Cache.update` calls must not multiply them. A final sampled token not yet represented in KV stays pending with its original tag and position; consume it exactly once on the next call before appending new message tokens. Forward the pending token under the epoch that sampled it (R_t), then commit R_{t+1}.
12. For request t, derive `R_t`: versions superseded/cancelled/completed for its scope, plus task versions currently suspended. For every layer/head and every new prefill/decode query, key column j is masked (boolean False / dtype-min additive), never a finite penalty, iff `origin_j=own_output` and `versions_j ∩ R_t != ∅`; otherwise it remains allowed subject to ordinary causal/padding masks. Here dtype-min is the backend's hard-mask representation, not a tunable attention penalty. Never mask new live output columns merely because old ones were released.
The union rule is deliberately coarse: retiring any one live rule can hide an answer that also contains useful facts or still-valid work. It is not evidence of actual causal dependence. User/tool facts remain visible, but assistant-origin facts can be lost to attention; the gate measures this collateral cost.
13. Call the trunk's standard autoregressive generation machinery ONCE per request; `forward` applies the mask on every step. This means one `generate()` call with normal prefill and token forwards, not literally a single forward for a multi-token answer. No LLM updater, hidden rewrite generation or second answer pass. Return reply plus the same custom cache and diagnostics.
14. Commit the validated register/render/tag epoch atomically before first prefill. On a preflight extension error, discard the staged update and fail OPEN: no FOCUS-3 injection/release, all historical columns visible. After prefill starts, preserve its committed epoch; a recoverable mid-decode error disables further release, preserves already-injected text, and marks the reply degraded without rollback or regeneration. Fatal trunk/cache corruption propagates the normal error, not fabricated success.
Fail-open is today's unrestricted-attention behavior, not a guarantee of identical tokens to a fresh baseline: previous recaps and masked-computed KVs remain. Cache provenance/epoch mismatches disable the extension for that session rather than silently reconstructing invented tags.

## 2. Mask equivalence, structure and prefix caching
For finite Q/K/V with at least one allowed key, softmax over logits with excluded entries set to `-inf` equals softmax over the surviving entries. Thus the proposed mask is mathematically equivalent to deleting JUST those columns while preserving survivor K/V, causal order and absolute RoPE positions; kernels may differ numerically. It is not equivalent to rebuilding an edited text history.
Check 35's `evict_answers` and check 37's `body_eos/surviving` arm are this mask
by construction (generated tokens + EOS removed, positions and survivor K/V kept,
renderer text retained): check 37 body_eos/surviving scored 31/30 at the releases
and 32/32 at both neutrals with 1 broken episode, equal to intact (n=32, one sort
task). Its `rebuilt` mode (28/23, 11 broken) rebuilds the malformed text history
and does not apply to a mask that never rebuilds. Check 35 S4 (28 -> 17 after two
evictions) was measured with unanswered filler user turns and does not transfer
cleanly. Check 39's placeholder repair writes a new "." column and is not this
primitive; do not cite it as validation. What no check tested: masking with
renderer recaps in the request, multi-rule union masks, and un-release (D5).
Evidence: [check 35 review](check35-review-fable.md), [check 37 results](quick-checks/check37/README.md), [check 39](quick-checks/check39/README.md). “Equal to intact” refers to the broken-episode count; intact release/neutral counts were 30/30/32/32.
Nothing is removed, overwritten, compacted or re-rotated: cache length and explicit `position_ids` advance over ALL columns, including masked ones; never derive positions from the release mask's cumulative sum. The mask is a request-local view and may change at a later task switch. History storage/context use still grows; this is no memory-capacity saving.
Un-release (task resume, exception expiry) produces columns that were computed under a mask now lifted; no check has measured that state. The gate's task-switch family is the first measurement; report its final-task success separately from the other three families. One-reply exception expiry is cut from v1; lifting a task-scoped exception or resuming a task can still un-release columns. Log un-release events and affected column counts explicitly.
Reuse old prefix K/V exactly as computed; surviving user/header/recap columns can still encode stale-rule effects, as [checks 35/36](check36-review-fable.md) caution. Old rule text/recaps remain visible; same-request live rendering is the proposed countermeasure, not a claim that stale information vanishes.
Prefix reuse requires identical token IDs, positions AND the historical mask/provenance trajectory that produced the KVs. Token-only cache keys are insufficient across sessions with different register histories. Forks may share immutable prefix tensors, but clone register/events/tags and keep the new mask private; never mutate a shared prefix's mask in place.
Because the recap is rendered inside every user message, cross-session sharing already stops at the first request, so the practical loss is small.
CPU acceptance for the eventual implementation: masked-vs-sliced attention with nonempty exclusions across layers and retained positions; disabled-extension logits vs ordinary trunk; own/user/tool/EOS tagging; multi-rule union; task suspension/resume (bookkeeping only, not evidence for un-release answer quality); partial-scope override; `none`, overflow and injected errors; pending-final-token alignment; independent cache forks. Test the public `generate` consumer, not just tag writers.

## 3. One Hugging Face repository
`Focus3Config(Qwen3Config)` uses `model_type="focus3_qwen3"`; `Focus3ForCausalLM(Qwen3ForCausalLM)` overrides `generate` and `prepare_inputs_for_generation`, with mask plumbing inside `Focus3Model.forward`. `Focus3GenerationOutput` exposes `text`, token sequences, `past_key_values`, and fail-open/update diagnostics.
Concrete hooks for the pinned Transformers 5.16.1 API:

- `Focus3Cache(Cache)`: `Cache.__init__(layer_class_to_replicate=DynamicLayer)`; `DynamicLayer.update` is `torch.cat` append-only; `get_seq_length`/`get_mask_sizes` return the physical length, which is what the design needs. `generate` keeps a user-passed cache untouched (`_prepare_cache_for_generation` returns early on `model_kwargs["past_key_values"]`; tuples raise). Add the register, provenance tags, event log and pending token as plain attributes; override `crop`, `reorder_cache`, `batch_repeat_interleave`, `batch_select_indices` to raise (they are the beam/assisted/continuous-batching entry points).
- Positions: `Qwen3Model.forward` derives `position_ids` from `past_key_values.get_seq_length()` when none are given, and 5.16.1's `prepare_inputs_for_generation` does NOT compute them from an attention-mask cumsum (it only passes `position_ids` through). Those forward defaults advance over all physical columns. Source-verification qualification: the separate `GenerationMixin._prepare_position_ids_for_generation` DOES use `attention_mask.long().cumsum(-1) - 1` when a mask is supplied. Always supply explicit physical `position_ids` before calling the trunk generation machinery, as section 2 requires, and preserve physical increments on decode; do not rely on the forward default through `generate`.
- The mask, two viable routes: (i) a 2D `attention_mask` of shape (1, past+q) with 0 at released columns — `create_causal_mask` ANDs it in as `padding_mask_function`, constant across queries, exactly R_t's semantics; or (ii) `create_causal_mask(..., and_mask_function=lambda b,h,q,kv: allowed[b, kv], allow_is_causal_skip=False)` inside an overridden `Focus3Model.forward`, passing the result as `attention_mask={"full_attention": mask}` (`Qwen3Model.forward` skips mask creation when it receives a dict). Route (ii) uses the vmap path (torch>=2.6). Either way, the override must live in `forward`, because `generate` builds the mask dict itself only for compileable caches. Choose route (i) for v1; route (ii) is the documented alternative, not an outcome-selected gate variant.
- Attention backend: `flash_attention_mask` returns None or the 2D mask and FA2 un-pads from it, so interior zeros corrupt the sequence rather than mask it; flex needs a BlockMask. Raise unless `config._attn_implementation in {"eager","sdpa"}`.
- Second weight file: `from_pretrained` loads only files named in the safetensors index, so `classifier.safetensors` is ignored by the trunk loader; fetch it with `transformers.utils.hub.cached_file(repo, "classifier.safetensors", revision=...)` in an overridden `from_pretrained` classmethod and build the two BERT branches from a config inside the bundle. Both classifier branches' tokenizers load via `AutoTokenizer.from_pretrained(repo, subfolder="classifier_tokenizer")`, pinned to that same revision; the trunk tokenizer loads from the repo root.
- The custom loop: choose overriding `generate(messages=...)` on the remote-code class. The sanctioned alternative is the hub `custom_generate/generate.py` mechanism (`model.generate(custom_generate=repo, trust_remote_code=True)`); v1 uses the class override only.

Files: `configuration_focus3.py`, `modeling_focus3.py`, `cache_focus3.py`, `relations_focus3.py`, `__init__.py`; `config.json`, `generation_config.json`; the unchanged Qwen trunk safetensor shards/index; and ONE additional `classifier.safetensors` bundle containing the relation branch and frozen admission branch.
Also ship trunk tokenizer assets/chat template, classifier tokenizer assets/config under `classifier_tokenizer/`, `relation_config.json` (labels, thresholds, scope grammar), `requirements.txt`, `provenance.json` (hashes, exact revisions/data lineage) and a model-card `README.md` with limits and license notices. Custom loading/saving explicitly handles the second weight file; trunk state-dict names/values stay unchanged and their hashes must match the frozen base. All branches run in eval mode; trunk parameters remain frozen.
Pin the tested software build (local lock: Transformers 5.16.1, PyTorch 2.13) and attention backend; run only via `uv run` in the pinned environment, since system `python3` has a different Transformers version. ```python

With a cache, `messages` means only newly arrived messages; the wrapper appends its own prior reply automatically. Without one, start a new session. Do not resubmit already cached messages. `past_key_values` round-trips the complete register/tags/event log and pending token, not a legacy KV tuple. [HF cache interface](https://huggingface.co/docs/transformers/main/en/cache_explanation)
First ship supports a single process, one session per call, greedy decoding, non-sliding dynamic cache and a tested eager/SDPA path accepting the mask. CPU classifier inference is separate from trunk device placement. Direct bare `forward` calls do not perform conversational updates.
vLLM/SGLang/TGI cannot run this package without a dedicated engine adapter: they
load architectures from their own model registry (trust_remote_code only affects
config/tokenizer code), their paged/flash kernels take no per-column mask,
automatic prefix caching and RadixAttention key K/V blocks by token IDs (section 2
violation), and their OpenAI-style chat endpoints are stateless, so there is no
carrier for `Focus3Cache` between calls. Beam, assisted/speculative decoding and
continuous batching call `crop`/`reorder_cache`/batch selection, which this cache
refuses. Cache quantization/offloading rewrite layers and drop the tags.
Also reject multi-process serving that strips custom caches, legacy tuple conversion, automatic context eviction and FA2/flex backends. One download is not universal serving compatibility.

## 4. Pairwise classifier and admission
Model: reuse the [fine-tuned bge-small recipe](quick-checks/finetune_classifier.py) architecture: 384-dimensional CLS plus role features, dropout .1, linear head. Initialize the separate relation encoder from base `BAAI/bge-small-en-v1.5`, not `model/ft/encoder`; train its five-way head/encoder on new relation data only. The existing rule/fact/none encoder AND head ([frozen assets](../data/classifier/model/ft/metrics.json)) stay frozen in the admission branch, so relation training cannot silently change admission embeddings and only admission carries the disclosed development history. Pin the base encoder revision in provenance.
Future recipe: one seed 9054301, three epochs, batch 32, AdamW lr 3e-5, weight decay .01, 6% warmup, gradient clip 1; extend the pair limit from 192 to 512 encoder tokens, explicitly a new recipe setting. No seed sweep or best-held-out checkpoint selection; use the final epoch. Rewrite into import-safe entry points; NEVER import/run the existing top-level fitting script to obtain helpers.
Input A is canonical `[rule id/key/version; scope/task/status] {original rule text}`.
The pair unit is (target version, candidate span). B is `[previous user]
{prev_or_empty}\n[user] {new_user_message}\n[span] {candidate sentence}`, the
candidate coming from the existing sentence splitter; the label applies to that
span against that target. For k spans and m eligible versions batch k*m pairs,
k <= 4 and m <= 16 (overflow -> none + diagnostics). `supersedes` uses the
classified span verbatim as the replacement text; `reinstates` copies the
referenced original; `cancels`/`completes` need no text.
Previous user context helps resolve references but has no new authority. Bound each full pair to 512 tokens; no truncation of decisive evidence: overlength produces `none` plus diagnostics and blocks fresh-key admission for the affected span. The 64 retained-version storage cap is distinct from the 16 eligible-version comparison cap; do not silently retrieve a convenient subset on overflow.
Outputs are pair labels `none/supersedes/cancels/completes/reinstates`. `new-rule` is a separate MESSAGE-level admission decision, never a sixth mutually exclusive relation to an old rule. A message may change one existing rule and add an unrelated one; process disjoint source spans in order, or abstain on ambiguous span assignment.
Rule identity comes from the classified target ID: accepted replacement inherits that key; a new rule gets an opaque stable key. The existing sentence-span splitter supplies candidate verbatim text; accept a replacement only when its rule span and target are unique. A small deterministic scope/reference grammar binds explicit lifetimes and known task names; uncertain bindings abstain. No gold task IDs, answer-dependent matching or generative extraction.
Key identity follows the conflict-test definition in LABELS-RELATIONS.md: incompatible requirements on overlapping scope or explicit replacement/withdrawal share a key; compatible additions are none + new-rule; different subject matter means a different key. “Mismatched scope” means a different task, not a task exception to a global rule. These are label semantics, not a lexical runtime veto.
Decision rule fixed before held-out/gate outputs: accept a non-none pair label only if `p >= .98`, with permitted role, valid status transition, unambiguous target and scope. Otherwise return `none`. Thresholds are conservative proposals, not certified error probabilities; publish precision, recall, coverage and abstentions by label/scope on held-out data. Ambiguous spans/targets still abstain even with high class confidence.
`new-rule` reuses P(rule) from the frozen three-way admission logits, requiring `P(rule) >= .95`, a resolvable persistent scope, and every existing-key comparison confidently none (`P(none) >= .98`). Exact repeated rule spans are idempotent; any uncertain/non-none comparison blocks admission under a fresh key. Do NOT use `ClassifierScorer`'s current scalar P(rule)+P(fact): facts must not enter the rule table.
“Fails safe to none” protects against relation-driven retirement, not contradictory admission: the frozen admission head also calls cancellation/replacement sentences rules. A confidently wrong none relation can therefore admit an update beside its live predecessor. A span admitted as new-rule while any eligible version of the same task/global scope is live is flagged `admitted_beside_live` in diagnostics; the gate reports the count. This broad flag also counts compatible additions; gold contradictory-recap episodes are scored separately. Do not add a lexical veto.
Only new persistent keys need that admission gate. Accepted relations use a unique verbatim replacement span even when its admission score is low; reinstatement copies the referenced original. Single-reply constraints are none for every pair and for persistent admission; handle them from current request text without a register exception or next-turn expiry. Tool/quoted/hypothetical prose cannot retire user records; conflicting labels/targets abort the span's transaction, with no label-priority tie-break. A reinstatement's live-version none row is consistent with derived shadowing, not a conflict.
CPU latency estimate, UNMEASURED: roughly 0.1–0.5 s/turn for eight short pairs plus admission; 1–3 s near 64 long pairs on a capable desktop CPU. Record p50/p95, pair/token counts and end-to-end overhead on the actual host; these are planning ranges, not an SLA. Two small encoder branches cost more storage than one but preserve admission behavior.
Data contract: [LABELS-RELATIONS.md](../data/classifier/LABELS-RELATIONS.md). Existing post-development evaluations remain evaluation-only; their prompts or responses cannot improve this classifier.
