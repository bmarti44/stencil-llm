The WORKLOG lineage line (WORKLOG.md:2415) states the finder is fit on `data/b3/{train-v43,cal-v45,mt-train-300}.jsonl` **and "b3-derived buried variants"**. So the shipped policy (d) weights were fit on the same generator, the same 40 topics x 3 phrasings (data/b3/base-texts.json, train-manifest "base_texts"), the same 21 constraint families, and the other parity half of the same attachment-template list that produces S2. Consequence: if (d) wins G0 and is "applied UNCHANGED to the gate benchmarks", the S2 leg is in-template. Fix in section 6.

## 2. Oracle validity

- Eviction plumbing: the registration and brief say `QwenFocusCache.evict`; **no such method exists** (src/stencil/qwen_cache.py defines write/read_inj only). The method is `KVCache.evict` (src/stencil/qwen3.py:70-85). It index-selects surviving columns in every layer, does not reduce `length`, and later tokens keep their original absolute RoPE positions (qwen3.py:73-75, 314-316, 343) — no re-indexing, no position shift. This is the deployment-matched semantics; only the name is wrong. LOW, fix the text.
- **F6 — MEDIUM. Attention sinks are evictable.** Candidate spans are role-stratified and the system message begins at column 0; nothing in the registration, brief, or `build_candidate_spans` (g0.py:110-170) excludes columns 0-3. Evicting the sink produces a large NLL increase that is not "need" and will land in the system-role utility distribution and in the null p90. Register: columns [0,4) are never inside a candidate or a null span, in every policy.
- **F7 — MEDIUM. Null spans may overlap their candidate and other candidates.** `match_null_spans` (g0.py:172-222) excludes only the exact (start,end) pair; for a role with one message (system; the current user turn) the "null" is the same message shifted by a few tokens, sharing most columns with the candidate. Null utility then tracks candidate utility, inflating null p90 and biasing readout (2) toward "uninformative". Register: a null shares no column with any candidate or other null; if no such window exists the candidate is dropped (not the constraint).
- **F8 — MEDIUM. Current-turn spans are candidates.** `age_bucket(0)` is allowed; the last user turn can be a candidate. At deployment the current turn is never evicted, policy (b) trivially keeps it, and policy (c) uses it as the BM25 query (retrieving itself). Register: candidates and nulls have age >= 1; the current turn is protected in every policy and excluded from B.
- Self-distillation reference (chat): sound as a label-free target, with two caveats to write down. (i) NLL_full on the model's own greedy path is near its floor, so deltas are small and dominated by the current turn; a failed signal check on chat is plausible for benign reasons — this is fine only if readout (2) is per corpus and the chat result is reported, not used to kill the tool arm. (ii) The greedy reference must be generated in the same non-thinking template used at scoring (`<think>\n\n</think>` prefix as in scripts/bfcl_mt.py:143); the brief does not say so. LOW.
- Tool reference: mean NLL over the rendered `<tool_call>` JSON includes boilerplate tokens (`{"name":`, `"arguments":`) that no span can affect; they dilute utility toward zero. Report utility on argument-VALUE tokens as the primary and whole-call as secondary. LOW-MEDIUM.
- Non-additivity/masking: the top-3 joint check is present; duplicated literals across turns (user constraint restated by the assistant) mask single-span LOO. Report the joint/sum ratio and the per-role masking case; no change to the rule. LOW.

## 3. Decision rules

- **F9 — HIGH. The signal threshold equals the null expectation.** Readout (2): signal exists iff fraction of candidates with utility above the null p90 "exceeds 0.10". Under the null, by definition of p90, 10% of null-distributed values exceed the null p90, so the registered threshold is the expected value under no signal. With 30 x 12 = 360 candidates, the one-sided 95% bound under the null is 0.10 + 1.645·sqrt(0.1·0.9/360) = 0.126 (46/360); a defensible registered threshold is >= 0.20 (72/360) or a one-sided binomial test p < 0.05 against 0.10, applied per corpus. As written, a 0.11 result "passes".
- **F10 — HIGH. The fixed budget B is oracle-derived and undefined for the gate run.** The registration says "one fixed budget B"; the brief defines B = "total tokens of the top-25% candidates", i.e. B depends on the oracle utilities of that dialogue, so (i) the policies are scored against a budget that already leaks the oracle's ranking, and (ii) no such B exists on Multi-IF/BFCL where no oracle is run. Register B as a fixed fraction of prior-context (age >= 1, non-protected) columns — e.g. B = 25% of evictable columns — computed identically in the pilot and in the gate run.
- Recovery ambiguity (MEDIUM): (a) "null-adjusted" is implemented paired (utility_i − max(0,null_i), clipped; g0.py:225-238) — state that, and that the un-adjusted number is secondary; (b) aggregation is unspecified — micro (pooled sums over all dialogues) vs macro (mean of per-dialogue ratios) can differ by >0.1 when a few dialogues carry most utility; register micro with macro reported; (c) "retains" is unspecified for column-level policies (b) and (e) — register: a span is retained iff all its columns are kept (partial retention counts as evicted).
- Tie rule (LOW): if two policies clear 0.80 on both corpora, the registered selector is the one with the higher min-over-corpora null-adjusted recovery; ties broken by simplicity order (a) < (b) < (c). (d) and (e) are ineligible (F2).
- Decision boundaries 0.80 / [0.50,0.80) / <0.50 are otherwise clear. The 6 GPU-h projection rule for the 1k oracle is fine; note the brief's 4 GPU-h pilot cap is a different number for a different job.

## 4. Minimality and speed

30+30 dialogues with <=12+12 spans, one full prefill, 24 evictions and one joint replay per dialogue (26 teacher-forced passes) is the right size; the 2+2 timing gate is correct. Cuts: cap pilot context at 8k tokens (not 16k) — the 16k cap only buys time, not signal, at 30 dialogues; drop the BFCL parse/match readout for the pilot (APIGen calls are not BFCL calls; keep top-1 agreement). Adds (all cheap, all needed for the readout to mean anything): F6 sink exclusion, F7 non-overlapping nulls, F8 age >= 1, F9 threshold, F10 budget definition, the content-overlap test (F4). Do not add G0' gradient attribution or more policies now.

## 5. What may be claimed if a zero-training policy wins

Claimable: "a retention policy with no trained parameters, chosen by oracle recovery on two public corpora (OASST2, APIGen-MT-5k) that were never the gate benchmarks, was applied unchanged to Multi-IF and BFCL V3 multi-turn; the gate results are out-of-selection-corpus transfer." Not claimable: "generalizes" beyond the two benchmark families; "benchmark-blind design" (F5); any G1/probe/"waves select" language; anything about S2 unless F1 is fixed. The model card must state: fit-on corpora with revisions, shas and licenses (CC-BY-NC-4.0 for APIGen-MT-5k => non-commercial artifact; OpenAI-terms clause), the τ-bench airline/retail origin and its adjacency to BFCL travel_booking; that policy (d) is fit on IFEval-taxonomy synthetic data and is reported as a control; that the policy family was designed after inspecting Multi-IF/BFCL behaviour; the single-turn negative scope condition (LEDGER-PLAN.md:325-326); the harness precondition (schemas never evicted in any arm); and, for S2, its template lineage.

## VERDICT: SOUND-WITH-FIXES

The core design (label-free counterfactual KV-eviction oracle on disjoint corpora, zero-training policies first, G1 conditional) is sound and the eviction primitive is position-faithful. The registration cannot be run as written because one lineage statement is false (F1), one registered number is the null expectation (F9), and the scoring budget is undefined for the run it governs (F10). The 2+2 timing run may proceed; the 30+30 records should not be produced until the span rules (F6-F8) are in the code, or they will have to be regenerated.
