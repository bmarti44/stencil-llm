## 2. Diagnosis

### (1) Admission misses (81) and false spans (34)

Miss composition, by my classification (family x mechanism):

| family | `[]` emitted for whole message | overlapping pred consumed by sibling gold | total |
|---|---:|---:|---:|
| rule_plus_payload | 35 | 0 | 35 |
| buried_rule | 20 | 0 | 20 |
| two_rules | 14 (7 messages) | 12 (11 messages) | 26 |

No miss involves a rejected or truncated output. In the 62 `[]` messages the gold rule starts at 50-80% of the message in 59/69 cases: a request or CSV/chatter payload first, the standing rule after ("Calibrate this one for me: ... Also, please treat any date with an error over 50 years as low confidence in future writeups." -> `[]`). This is a whole-message abstention, not a span-boundary problem, and it is the exact pattern the only payload example in few-shot.json teaches: example 2 is a mixed request + quoted payload whose answer is `[]`; there is no mixed request+constraint positive, although the prompt says "Mixed request+constraint: extract the constraint". A "one span per clause" instruction or per-clause decoding would address at most the 12 broad-span misses (78.96% -> at best 316/385 = 82.1%), still under the 85% bar; it cannot touch the 69.

False spans: 22 lie in gold-positive messages (19 `rule_plus_payload`: the one-off request itself admitted as a `task:<name>` rule, e.g. "Log these weights for the week: Mon 612 ...", "Draft the briefing for the reef wall: ..."; 3 `two_rules` fragment duplicates overlapping an already-matched gold), 6 are the payload template, 6 spans are the four assistant echoes. So the trunk's precision problem is semantic on positive messages, and the same confusion (request vs constraint in one message) produces both the 35 payload misses and the 19 payload false admissions.

### (2) SETUP 58/96 false turns

All 96 rows are user role, so an authority/role check removes nothing here. Composition of the 58 turns: 39 template-only (`Work on task X; Sort request for task X: payload [...]; reply as compact JSON ...`, `Reply exactly set.`), 8 template + inert-quote, 5 template + other, 5 other-only, 1 inert-quote + other. "Other" = 3 lines quoted inside `Inert setup context: the line "For task X, sort the payload in descending order." is not an instruction.`, 2 cancels turns and 4 completes turns emitted as `add` (an artefact of the empty-register diagnostic: with no target the model had no legal relation op and chose add over none), and 2 sub-word fragments (`Continu`, `sort`). A request-kind gate on the template touches 52/58 turns; adding a quoted-span gate and running cancels/completes against a populated typed register (where they become relation ops, not admissions) leaves the two fragment turns, i.e. <=2/96 mechanically. Caveat: that gate is keyed to our own synthetic template and does not transfer; on the authored bank the same request-as-rule confusion produced 19 false spans with no template to key on. Also note that 55 of the 58 false turns are gold-empty request turns: the trunk treats a formal work request as a task rule, which is the identical failure in both banks.

### (3) Task-over-global 0/21

All 21 rows: register holds a live global rule; message is "For the show cards, English style names only, no Japanese." style. Output in every case is `add` with the register's own key (18 `task:<name>`, 3 `global`; the 3 global adds also violate "Do not add a duplicate"). The model identified the same key and the new scope and still chose add. Two prompt-side causes: the only supersedes clause reads "replaces a live same-key rule on overlapping scope, including explicit task override of global", and a task scope is naturally read as not overlapping a global one; and none of the six exemplars shows the case (the supersedes exemplar is a same-scope value swap). LABELS-RELATIONS.md itself says the global rule "remains applicable elsewhere", which is semantically an add-with-shadowing; a fitted model learns the label convention, a zero-shot one will not without an exemplar. Verdict: prompt/taxonomy-exemplar gap, not a capability limit (the withdraw_replace, bare_value_temporal and actually_B families are 36/37). Two design notes for the typed register: whether the 21 should be represented as supersedes-on-intersection at all is a register-semantics choice, and the relations bank hands the trunk a one-rule register, so target identification (285/285 = r1) is untested. Remaining relation errors: cancels -> supersedes 7 ("Leave X off ... from now on", "just plain text" read as a replacement value), cancels -> none 7 (five emitted nothing, e.g. "Stop signing off altogether." -> `[]`), reinstates -> none 3 / -> supersedes 3, completes -> none 2, none false positives 5.

### (4) Comparison with the fitted classifiers

Same banks (heldout-3: 357 messages / 385 spans; relations heldout-3: 448 rows / 172 supersedes).

| system | admission R | admission P | relations acc | supersedes R |
|---|---:|---:|---:|---:|
| check44c C2 (bge-small BIO) | 64.16% | 77.67% | - | - |
| check44c B head | 60.3% | 99.1% | - | - |
| relations v2 (v3) | - | - | 87.95% (87.05%) | 73.26% (73.26%) |
| check46 trunk, zero-shot | 78.96% | 89.94% | 89.06% | 87.21% |

Yes: the unfitted trunk is the best admission recall (+14.8 points over C2) and the best supersedes recall (+14 points) we have, and its error shape is complementary to 44c's: cue-less 84.91% (44c: 52%), three-rule single sentence 94.87% (44c: 37%), but it abstains on rule-after-payload messages that a BIO tagger handles locally. Caveats: the task shapes differ (the trunk produces a whole operation; the classifiers score gold spans or tokens with the target supplied), the model is roughly 10x larger, and the 4/36 "quoted" figure is entirely assistant echoes that a role gate removes. Implication for check 48 (fitted 4B updater): the recall floor to beat is 78.96%, the precision floor 89.94%. Reaching 85% recall needs +24 spans, and the pool is concentrated (55 rule-after-payload/buried misses in 62 messages, 12 broad spans); reaching 95% precision needs FP <= 16, i.e. removing most of the 22 request-as-rule spans. Both are exactly the "extract the constraint, not the request" distinction, so headroom depends on whether the reconciled fit corpus contains rule-after-payload positives with the request left out; check44c (fitted, 64%) is the warning that fitting on the current corpus underperformed a zero-shot 30B on recall, so corpus coverage is the gating item, not architecture. Expected headroom if that coverage exists: recall into the high 80s, precision in the low-to-mid 90s; the 95% precision bar is the harder one. A cheaper alternative worth registering alongside check 48: trunk as proposer plus a small fitted verifier on (span, message) pairs for precision, the C-then-B analog.

### (5) Latency

Mean 6.0 s per user message is entirely output-length bound. Calls whose output is `[]` take 0.63 s mean (n = 281), which bounds prefill of ~1,450 tokens plus grammar compilation; non-empty calls average 93 completion tokens in 8.0 s, i.e. ~12.9 tokens/s per request; corr(seconds, completion tokens) = 0.966, versus 0.42 with message length and 0.26 with prompt tokens. Engine-level generation throughput in server.log is 31.8 tokens/s mean (33.9 with four running), which is not below the vllm-qual baseline for the same image and flags without a grammar (25.1 mean / 49.6 max), so the per-message substring grammar is not the bottleneck; the batch-invariant bf16 MoE decode rate is. Prefix caching is already on (`--enable-prefix-caching`, minimum prompt 1,391 tokens shared), so shorter register rendering or schema/few-shot caching cannot recover much below the 0.6 s floor. What would help: cut output tokens (span copies are 30% of output characters, key/kind/value 21%, JSON scaffolding the rest; emitting start/end offsets or sentence indices and dropping kind/value roughly halves output, ~3-4 s mean), a compact line format instead of JSON objects, and dropping VLLM_BATCH_INVARIANT in a production path where cross-batch determinism is not needed. For an async assistive proposal that appears while the reply streams, 6 s mean is acceptable; p95 15 s (multi-rule SETUP-style messages average 11.8 s, max 32 s) is not acceptable for a synchronous gate on the reply.

## 3. Disposition

NO-GO is correctly applied: every registered bar was committed before the look, none was changed after, and neither half passes (admission fails recall, precision and all three false-admission rates; relations passes supersedes recall but fails accuracy 89.06% < 94%, needing 421/448; SETUP fails on false turns). PARTIAL requires exactly one half passing, so it was correctly withheld.

Claim boundary: one frozen prompt on a one-rule register with the target id trivial; no key/kind/value/scope accuracy claimed (scope is mostly wrong); latency is a concurrency-4 batch-invariant measurement, not a request-latency SLA; the SETUP result is an empty-register diagnostic whose cancels/completes turns are structurally unfair to an updater; both held-out banks are now exposed to this prompt, so any prompt change needs a fresh author-disjoint bank.

The ONE change most likely to reach PARTIAL: add one task-over-global exemplar to few-shot.json (live global rule, "For the <task> only, <new value>" -> supersedes on r1 with task scope). The 21 misses of that single family are 21 of the 22 rows separating relations from its 94% bar (420/448 = 93.75%); one more correct row from the seven "Leave X off ... from now on" cancels -> supersedes confusions, which a one-line clarification in the same edit addresses, crosses it, while supersedes recall would go to 171/172. For the admission half the analogous lever is a mixed request+constraint positive exemplar with the rule after the payload and the request not admitted (targets 55 misses and 19 false spans at once), but admission needs three bars to move together and is the less probable path to PARTIAL; GO additionally needs SETUP, which no prompt change reaches without the request-kind and quoted-span gates.
