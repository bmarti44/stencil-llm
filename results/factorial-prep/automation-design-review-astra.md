## The hypothesis worth testing

Brian's correction is scientifically coherent: replacing per-update manual maintenance can be valuable even if good manual prose remains the quality ceiling. Internal versioned state may render ordinary prose. The immediate question should be:

> Given an authenticated natural conversation and its own evolving state, can one frozen-trunk updater per message maintain all currently governing obligations without per-turn human corrections, so a worker produces useful code at an acceptable measured quality and inference cost?

This changes the intervention from **gold register versus gold prose presentation** to **predicted maintenance versus supplied correct maintenance**. Manual prose is an oracle quality reference. It need not lose for automation to be useful. A later automatically maintained prose arm distinguishes automation in general from benefits of versioned storage; do not require it to answer the first inexpensive feasibility question.

## Findings

### automation-design#1 — medium, open prerequisite for a model runner: finish the proposal-to-transaction contract

The draft correctly separates research inference from production adoption. `loop.authenticate` requires explicitly adopted structured entries, and `Register.apply` documents a trusted structured caller. A future compiler must not set `Message.adopted=true` to make inferred operations pass that boundary. Record the distinct research policy: authenticated direct-user messages are eligible for inferred changes; interpretation can still be wrong. User-provided quoted material does not inherit adoption merely because its containing envelope is user-role.

Before freezing a runner, specify evidence spans, operation ordering/conflicts, ID allocation and caps. Host source IDs, role, registered task handles and completion receipts cannot come from model-written authority fields. Existing targets come from the actual displayed predicted state. A task-local override uses an existing obligation key with a narrower scoped add; it does not retire the global rule. Same-scope replacement targets the exact live version. Reinstatement copies the actual retired target's immutable value/text and creates a new version. The base hash must identify the actual complete pretransaction state: `Register.generation` is a request clock, not a state revision. The contract already recognizes these points; they remain implementation qualifications, not reasons to block its small CPU bank.

Use real system/developer entries for authority controls. `Register.defaults` are overridable fallbacks. Legal transitions and verbatim evidence establish mechanical validity, not correct interpretation of a negation, quotation, replacement or one-off request.

### automation-design#2 — medium, open prerequisite for an empirical claim: make trajectory success and intervention accounting primary

Checking extracted spans, one correct current view, or gold replay would leave the central hypothesis untested. The next model trial must begin with only declared initialization and thereafter carry predicted state forward, including rejected transactions and erroneous prior updates. No reset to expected state after each message, before each coding probe, or on a task switch. A later natural correction can repair an error but cannot erase the earlier trajectory failure.

Normal authored user requests and rule changes are the task input. Additional clarification, explicit adoption of an inferred proposal, edits to reminders/state, operator retries, or manual repair after seeing an answer are interventions. With interventions prohibited, zero intervention count is partly enforced by design; it becomes useful automation evidence only jointly with correct state and competent output. Empty proposals and rejected changes preserve integrity but fail when a required update is absent.

### automation-design#3 — low, declared scope limit: two DEV seeds do not cover completion or qualify the worker

The current two eight-round seeds exercise CPU authoring and state-consumer structure. Deferring completion is appropriate for this small deliverable. Label completion/evidence interpretation untested, and do not call those seeds complete coverage of every lifecycle action. Gold replay can validate annotation consistency; it cannot measure predicted maintenance or coding competence. Later task closure must be an actual authenticated user closure or a separately verified receipt, not a scheduled gold “success” event or assistant self-report.

No high/critical defect is identified in the corrected prospective contract. These findings do not require another process layer: implement the pending contract details, use meaningful controls, and qualify the actual consumer before freezing a model screen.
