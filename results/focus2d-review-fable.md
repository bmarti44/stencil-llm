## 2. The schema_invalid attribution

- 59 BOTH schema_invalid records: 58 at CLEAR, 1 at SWITCH (the truncated case). By cell: CLEAR/512/ascending 30, CLEAR/512/descending 27, CLEAR/0/descending 1, SWITCH/512/descending 1. So 57/58 CLEAR cases are in the delay-512 half (57/128 vs 1/128).
- It is NOT the FOCUS-2c tag omission. All 58 CLEAR outputs are a bare JSON array, and all 58 equal the payload exactly, i.e. the correct default value with the {"answer":..,"tag":..} wrapper dropped. The two non-BOTH schema_invalid records (neither, placement-only, both at NEUTRAL2/512) are the old tag-omission shape and are unrelated.
- The schema line and Keep-tag line are in the base system slot in 6,400/6,400 scored records, including all 59 failures. So the split-cue fix worked as registered (the carrier persisted) and the failure happens anyway.
- Rendered context at BOTH/CLEAR: every prior assistant task body is the "." placeholder (SET, PREHOLD, SWITCH, HOLD, BACK all evicted, since eviction is never undone), the only surviving non-placeholder assistant bodies are the tool call and the prose delay answer, and the current user turn reads "Return the payload list unchanged.\nAdditional requested keys: none.\nProcess this payload: [...]". With zero JSON-object exemplars left and a local instruction that literally says "return the payload list", the model returns the list. The 512-token delay (a 1,949-char prose turn plus a prose answer immediately before CLEAR) pushes the system schema line far back and makes the failure near-deterministic (57/128 vs 1/128).
- Cross-arm contrast pins the cause: eviction-only at CLEAR has the identical evicted context but the default rule sits in the system slot next to the schema line -> 253/256, 0 schema_invalid. Text-restate at CLEAR has the identical in-request default cue but retained exemplars -> 228/256, 0 schema_invalid. Only the combination (all exemplars evicted AND the default cue rendered in the request, away from the schema line) produces the bare array. This is an interaction of masking with cue placement/wording, not a renderer bug.
- Counterfactual (descriptive only, not a rescue): if the 58 bare arrays were counted as correct, BOTH all-five would be 182 vs text-restate 176, b/c 43/37, p = 0.29. Even without the schema loss, BOTH shows no advantage over text-restate.

## 4. Plain answers

(1) Is the verdict correctly applied? Yes. Every registered number recomputes exactly; the decision rule (b > c, Holm .05, >= 5 pp over text-restate; constraint gate p > .05 and h - r <= 2; F6 h <= 5) is applied as frozen. FAIL-SAFETY (unsafe context management, do not promote) is the correct prewritten reading. Text-restate's own limits are stated correctly; the analysis makes no equivalence claim. One presentation nit: outcome.md says "58 BOTH responses returned the payload as a bare JSON array ... 57 after a 512-token delay and one without" — correct, and the 59th is the truncated SWITCH case; the F6 table's schema_invalid 59 therefore double-counts that one truncation as both structural and schema, which the text discloses.

(2) What is the substantive finding, and is the 32-vs-176 gap due to the supersession/anti-imitation wording? No — the gap is almost entirely cadence, not wording. Placement-only renders the rule only at the three change events and nothing at HOLD/NEUTRAL2; text-restate re-renders at every request. At the checkpoints where both arms render an in-request cue, plain placement-only BEATS the anti-imitation recap: SWITCH 244 vs 225, BACK 249 vs 229, CLEAR 253 vs 228; on the three-checkpoint conjunction placement-only is 234 vs text-restate 183 (b/c 54/3, descriptive p = 2e-13). Placement-only collapses only where no carrier exists: HOLD 185 and NEUTRAL2 43 (at NEUTRAL2 it reverts to sorting: ascending 115, descending 24, default 43 — pure imitation of the retained sort demonstrations, because the old-slot rule was removed and nothing replaced it). So the all-five conjunction (capped by NEUTRAL2 at 43) drives 32. The correct reading: (a) an in-request rule is interpreted by this model as scoped to that request — it does not persist to later requests — so it must be rendered every turn or persisted elsewhere; (b) an explicit supersession/anti-imitation statement adds nothing measurable at the rendered checkpoints on this family (it is slightly worse than the bare rule, 19-25 fewer successes per checkpoint, though these arms also differ in cadence history, so treat that as descriptive). The text-restate "masking-equivalent" effect comes from restating the live rule at every request, not from telling the model to ignore its earlier answers. This is not a proof that the wording is inert (no arm isolates wording at matched cadence), but the evidence points that way.

(3) Is masking now shown unnecessary or harmful, and what would rescue it? On this family and this configuration masking is a mixed instrument: it helps exactly where no rule is rendered (HOLD: placement 185 -> BOTH 238; NEUTRAL2: 43 -> 256; eviction-only vs neither 108/0) and hurts where one is (SWITCH: placement 244 -> BOTH 213; BACK 249 -> 230; CLEAR 253 -> 198, the last via the bare-array schema loss). It also forfeits assistant-authored content (64/64 vs 42/64). Everything masking bought at HOLD/NEUTRAL2, per-request text restatement bought too (243/256) without the SWITCH/BACK/CLEAR cost. So on this evidence masking is unnecessary given a per-request carrier and harmful in the absence of exemplars. The missing cell is NOT "text-restate + masking": that cell would put the default cue in the request with all exemplars evicted, which is precisely the BOTH/CLEAR bare-array condition (eviction-only escapes it only because its cue sits in the system slot), so it is expected to reproduce the constraint failure. The genuinely missing and cheap cell is "placement-only rendered at every request" (plain live rule + obligations, no supersession wording, no mask), plus optionally the same block with the schema/tag lines repeated locally. The per-checkpoint rates (244/249/253 with a carrier) suggest that cell could exceed text-restate, but that is extrapolation across checkpoints of different difficulty, not a measurement. A rescue of masking itself would need (i) exemplar-preserving eviction (keep at least the most recent well-formed answer, or evict only bodies contrary to the live rule) and (ii) never placing a bare "return the list" instruction adjacent to the payload without the schema in the same block; whether that beats per-request text is an open empirical question with a small prior.

(4) FOCUS-3 ship design. Register the live-rule block for in-request rendering at EVERY request (not only at change events), carrying every live obligation in one block — task/default, schema, tag, request obligations — since the rendered block must be the sole thing the model needs locally (design lesson already in the 2d registration; 2d then moved schema/tag out of the block and still lost 58 CLEAR answers to a local-instruction/format conflict). Supersession statements are optional: no evidence here that they help, some that a bare rule is at least as good; if kept, test them at matched cadence rather than assume. The custom cache/mask is not needed to reach the best observed control on this family (text-restate 176 with no eviction, zero collateral failures); it should not be part of the ship path unless a future registered cell shows per-request placement + selective masking beating per-request placement alone with no constraint harm. Keep the token-map/mask machinery as an experimental arm, not as the default.

(5) Single next quick test. One registered 256-episode, three-arm run on the same frozen banks/seeds: (A) placement-every-request (plain live rule + obligations at all five checkpoints, no mask), (B) placement-every-request with schema+tag repeated in the block, (C) text-restate as the fixed comparator; endpoint all-five + the unchanged-constraint gate, McNemar vs C. About 3 GPU-h at the measured 2d cell cost. It answers both open questions at once (cadence vs wording; local schema repetition) and, if A or B >= C, closes the case for masking on this family.
