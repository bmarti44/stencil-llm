## 1. What the updater must learn—and what our data actually says

Brian's proposed mapping is a **structured state-transition transducer**: authenticated context + current register + current message → a set of grounded operations. A classifier can select operations, but a single class cannot also express an arbitrary number of new rules, their spans, replacement values and targets. A generative decoder or a joint span/relationship model can express the complete mapping. Generate deltas, validate them, then render the resulting state; do not regenerate and overwrite the whole rule table.

The closest published formulation is **Diable**, which represents dialogue state as a table and generates update operations from the previous state and dialogue context. Its reported 2.4× time improvement is against its DST comparators, not against our server. It directly supports the *interface*, without proving standing-rule admission accuracy. [Diable, Findings ACL 2023](https://aclanthology.org/2023.findings-acl.615/).

**Two data prerequisites before any fit.** First, the relation report explicitly discloses **90 inherited Astra2 evaluation-derived relatives** in the v3 pool. The approximate corpus total in the question is not a clean-fit manifest. Second, freeze the interpretation of **withdrawal plus replacement** before annotation or training. The existing definition makes cancellation a withdrawal *without* replacement. My proposed reading is: a committed persistent replacement for the same key and compatible scope is one atomic `supersedes`; withdrawal plus an unrelated new rule is `cancels` + `add`; ambiguous target/scope abstains. This is a prospective interpretation requiring a recorded label reconciliation, not a relabeling of evaluated examples. Likewise, a narrow-scope override must preserve the broader rule outside that scope; if the shipping validator does not support an intersection, it must reject it. [LABELS-RELATIONS.md](../data/classifier/LABELS-RELATIONS.md), [composition v2 §§1–2](focus-mechanism-composition-v2-astra.md).

**Do not fabricate complete-update labels from partial annotations.** A relation row's `none` means no change to *that target*, not an empty message-level operation list. Admission rows need audited key/scope/kind/value labels before supervising full JSON. Group complete annotations by source message; incomplete rows can supervise a task-specific relation output, but cannot silently supply whole-register gold. Add target distractors only from independently authored development scenarios. Existing one-rule relation tests do not establish multi-target binding, executable value completeness, or end-to-end register correctness.

**Full fit versus quick check matters.** At 10,000 examples × 512 total input/output tokens, one epoch is 5.12 million tokens. At 100/300/1,000 training tokens/s it costs **14.22/4.74/1.42 hours**, before loading, evaluation and saving. Two epochs double these numbers. Tokens receiving zero loss still consume forward computation; relation pairs are not independent complete messages. The ≤1 GPU-hour proposals in §8 are small fixed pilots, not promises to finish 8–12k examples. Measure actual lengths and ten-step throughput before spending the training allocation.

Shipping rankings favor D/A1 (one base load, small extra adapter) over B (second decoder), then C (small sidecar but a custom structured head). However, B/C can still live in **one HF repository** alongside a byte-identical trunk: package their configs/tokenizers/weights under subdirectories and call them through custom `generate`. One repository does not mean one network or one standard vLLM model. A vLLM endpoint does not automatically execute HF custom-generation orchestration; the package's controller must issue updater and base requests itself. No external agent/memory framework is needed.

## 3. A — A LoRA on Qwen3-30B-A3B itself

**Start with attention only.** Proposed first adapter: rank 16, alpha 32, zero dropout, `bias="none"`, `target_modules=["q_proj","k_proj","v_proj","o_proj"]`, causal-LM output loss only. Keep router, norms, embeddings, LM head and all original parameters frozen; no `modules_to_save`, embedding changes, weight merge or vocabulary expansion. The precise learning rate/epoch cap belongs in the pilot registration, not a later held-out search.

Qwen's config has 48 layers, hidden size 2,048, 32 query heads ×128 dimensions, four KV heads ×128, 128 experts and top-8 routing. Thus attention projections are **not all 2048×2048**. My rank-16 calculation is `48 × 16 × [2(2048+4096) + 2(2048+512)] = 13,369,344` trainable parameters: **25.5 MiB BF16 adapter storage**, or 51 MiB FP32, before metadata. Optimizer state remains small; activations and frozen weights dominate. [Qwen original config](https://huggingface.co/Qwen/Qwen3-30B-A3B/blob/main/config.json), [Qwen3 report](https://arxiv.org/abs/2505.09388).

**Expert MLPs are supported, but module layout matters.** PEFT documents Qwen3-MoE expert targets `mlp.experts.gate_up_proj` and `mlp.experts.down_proj` through `target_parameters` for fused `nn.Parameter` weights. Older layouts expose individual expert linear modules. Inspect the pinned model's actual names and exported tensors; `all-linear` is not proof that fused parameters were adapted. PEFT also warns about materializing expert deltas and inference overhead. [PEFT LoRA reference](https://huggingface.co/docs/peft/package_reference/lora).

Do not give each expert a dense-model rank by accident. Under independent per-expert factors, rank 16 on separate gate/up/down weights implies `48×128×16×3×(2048+768) = 830,472,192` parameters. A fused gate/up factorization instead gives **629,145,600**. These are illustrative layout-specific calculations, not an assertion of what every PEFT release exports. Both dwarf the 13.4M attention adapter. Lower expert ranks or shared factors change the count; log the actual trainable parameter count and tensor shapes. With ~10k short examples, many experts receive sparse task supervision; a gain over attention-only is a hypothesis, not a reason to train them first.

**BF16 first; QLoRA is not necessary in principle.** The qualified local load measured **56.88 GiB** of BF16 weights. Short-context attention LoRA may fit with gradient checkpointing, small microbatches and accumulation in a 128 GB unified-memory machine, but the whole 128 GB is not free GPU memory. Reserve space for the OS, Brian's resident server, temporary allocations and other consumers; do not assume a concurrent full vLLM KV pool can remain allocated during training. [Local qualification](quick-checks/vllm-qual/README.md), [NVIDIA Spark fine-tuning playbook](https://build.nvidia.com/spark/pytorch-fine-tune/instructions).

Unsloth reports ~63 GB for 16-bit Qwen3-30B-A3B LoRA and optimized MoE kernels, but these are vendor tests on other GPUs, not GB10 timing guarantees. Its MoE page currently discourages bitsandbytes 4-bit MoE training, while its Qwen guide still advertises a 17.5 GB path. That documentation inconsistency makes quantized MoE an implementation qualification task, not a default shortcut. [MoE implementation/measurements](https://unsloth.ai/docs/new), [Qwen guide](https://unsloth.ai/docs/models/qwen3-how-to-run-and-fine-tune). QLoRA's 65B-on-48GB result establishes the general technique, not this ARM64 MoE combination. [QLoRA, NeurIPS 2023](https://arxiv.org/abs/2305.14314).

**Serving status as checked 2026-09-06.** The dated vLLM engineering post explicitly supports **Qwen3-MoE multi-LoRA in v0.15.0+**. PEFT places initial fused-expert support at 0.11.2; those statements describe different maturity points, not a contradiction. The local qualified image is **0.19.2rc1.dev134+gfe9c3d6c5**, digest `sha256:3dbe092ec5b2cef63b6104d33fa75d6ce53a7870962529ada69f78bbbc38e776`, using BF16, `TRITON_ATTN`, and unquantized `TRITON` MoE. Its version is new enough for the documented feature family; its particular LoRA/backend/GB10 combination has **not** been qualified. [vLLM multi-LoRA engineering post, 2026-02-26](https://vllm-project.github.io/2026/02/26/multi-lora.html), [local receipt](quick-checks/vllm-qual/README.md).

Prospective launch *delta*, appended to the qualified flags, not a command executed here:

```text
--enable-lora --max-loras 1 --max-lora-rank 16
--lora-modules register-updater=/absolute/package/updater_adapter
```

Request `model="register-updater"` for updater JSON; request the base model's served name for normal generation. One adapter plus the base does not require two weight copies. Current docs also discuss mixed 2D/3D expert formats; do not copy newer format flags into the pinned image without checking it. Attention-only avoids expert export-layout friction. Static adapter registration is sufficient. [vLLM LoRA serving documentation](https://docs.vllm.ai/en/stable/features/lora/).

**Adapter off must mean original computation.** With only separate low-rank weights trained, the mathematical base weights remain unchanged. Nevertheless, prove the practical claim: hash base shards/config/tokenizer before/after fit; assert the optimizer has only adapter parameters; run an adapter-on effectiveness control; compare adapter-disabled logits/token IDs against the same-backend base on fixed DEV inputs. Test alternating and interleaved base/adapter requests. Identical weights do not automatically guarantee bitwise outputs across changed kernels, batching or quantization. Never merge/unmerge in the live trunk; do not globally toggle a shared HF model while concurrent requests run. Use per-request vLLM routing or serialize the HF adapter context. Cache namespaces must distinguish ordinary LoRA from base requests. The updater's transcript/output must not become a privileged instruction accidentally; only validator-accepted events reach the renderer.

**Published extraction evidence, including a genuinely small 32B study.** MedStruct-S reports **3,582 pages**, an 81/9/10 split (~2,901 training pages before task expansion), rank-8 attention LoRA, and greedy vLLM inference. Qwen2.5-32B's end-to-end Task-3 exact key/value score rises **0.4924→0.6867**; approximate key/value score **0.5537→0.7882**. Baichuan-M2-32B reaches **0.6884/0.7884**. This is close in scale and fitting method, but Chinese OCR extraction, page-level random splitting, and different metrics prevent transfer to our author-disjoint P/R bars. It reports no comparable GB10 training time. [MedStruct-S, 2026 preprint, §4/Tables 1–2](https://arxiv.org/html/2605.03103v1).

GoLLIE supplies a second 30B-class precedent: Code-LLaMA-34B, QLoRA on transformer linear layers, annotation guidelines encoded in the schema. Its supervised average is 75.0 F1 versus 73.0 for the 7B version; gains vary by task. Its 34B run used two A100s and 94.6 hours, so it is **not** evidence for a one-hour fit. Reuse the idea of learning the annotation contract, not its benchmark-trained checkpoint or corpus. [GoLLIE, ICLR 2024, Tables 2/10](https://arxiv.org/html/2310.03668v3).

## 4. aLoRA: usable technology, optional optimization

IBM's **Activated LoRA** trains an adapter that starts affecting tokens only at an invocation boundary; tokens before that boundary retain base-model KV. It is different from similarly named rank-allocation methods and cannot be obtained just by switching a conventional LoRA on halfway through a cached prompt. Its NeurIPS paper establishes this architecture. [Activated LoRA](https://arxiv.org/abs/2504.12397), [NeurIPS 2025 paper](https://papers.nips.cc/paper_files/paper/2025/file/4d0b6303d4a4811445f69f357bf6def5-Paper-Conference.pdf).

Practical support has three distinct levels:

| Path | What is available | Fit for our first experiment |
|---|---|---|
| **HF Transformers + PEFT** | Current PEFT has `alora_invocation_tokens`, causal-LM support and cache-reuse examples. The original IBM package is deprecated in favor of PEFT. | Usable prototype path for our custom generate; Qwen attention-target smoke still required. Rank 32 is a suggested starting point; no beam search or merging. [PEFT](https://huggingface.co/docs/peft/main/package_reference/lora), [IBM source](https://github.com/IBM/activated-lora). |
| **Research vLLM fork** | Published serving implementation with activation-aware execution/cache hashing, released in `tdoublep/vllm` branch `alora`. | Real available code, not merely “coming soon”; not proof of upstream or GB10 support. Requalifying a fork is too expensive for the first accuracy check. [Serving paper](https://arxiv.org/html/2512.17910v1), [fork](https://github.com/tdoublep/vllm/tree/alora). |
| **Granite Switch** | IBM's June 2026 release composes adapters with a switching architecture and serves through HF/vLLM. Current repository defaults to vLLM 0.19.1, with another extra for 0.20+/CUDA13. | Concrete deployable Granite path, not a ready Qwen3MoE adapter loader. It adds architecture/control machinery and would require a new trunk qualification. [IBM release](https://research.ibm.com/blog/granite-libraries-project-switch), [code](https://github.com/generative-computing/granite-switch). |

I did **not** establish a supported upstream aLoRA-on-Qwen3MoE path in the qualified image. Upstream's documented conventional LoRA path does not establish invocation-aware cache reuse; a read-only upstream tree/config check found no aLoRA-named paths or config field. That negative check is not proof of universal absence. Conversely, claiming “vLLM cannot run aLoRA anywhere” is now false because the fork and Granite implementation exist.

For our design, cache reuse has a strict boundary. The cached token prefix must match exactly, including chat template, positions and unadapted system text. A separate updater prompt beginning with a different schema/register is generally **not** the same prefix as ordinary generation. After invocation, adapted KV cannot simply be handed back as clean base KV: preserve/fork the pre-invocation prefix and recompute any needed suffix. The renderer can itself change the earlier prefix when the register changes. These facts limit savings on short compact updater inputs; aLoRA becomes attractive if measured long-history prefill dominates. The paper's very large latency gains are workload-dependent, not a prediction here.

## 5. B — Dedicated small generative updater

**Prefer Qwen3-4B for the first fit.** It can learn all six operations and variable-length lists with the same source-copying contract as the trunk, at materially lower residency and iteration cost. The frozen 1.7B's 2.75% recall says its prompted behavior failed; it does not measure supervised learnability. 1.7B remains a sensible later compression target if 4B succeeds. 8B is the intermediate escalation if 4B makes semantic errors but training/serving it is simpler than trunk adaptation. Base cards: [1.7B](https://huggingface.co/Qwen/Qwen3-1.7B), [4B](https://huggingface.co/Qwen/Qwen3-4B), [8B](https://huggingface.co/Qwen/Qwen3-8B).

Use non-thinking SFT, source-grounded JSON, rank 16, and output-only loss; dense attention+MLP LoRA is straightforward. Start BF16. Dense QLoRA is an optional memory remedy if simultaneous deployment requires it, but introduces a fit/serve quantization mismatch to measure. A small *dedicated* updater can be merged into its own base at export without modifying the trunk; preserve the unmerged adapter/source hashes as provenance. Avoid fitting reasoning traces when only operations are required: longer targets cost training and runtime tokens and are not audited gold.

**Relevant evidence.** LDST adapts a smaller open LLaMA foundation model using LoRA and domain/slot instruction tuning; its dialogue-state results are competitive with ChatGPT in its studied settings. It supports task-specific generative adaptation, but not an automatic 94% relation expectation. [LDST, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.48/). Low-resource prompt tuning also achieved competitive DST with less than 0.5% of the parameters of prior approaches; this favors parameter-efficient learning as a testable route. [Ma et al., Interspeech 2023](https://www.isca-archive.org/interspeech_2023/ma23g_interspeech.html). Neither study has our distinction between permanent rules, single requests, quoted directives and task completion. Diable's delta interface is more reusable than their label ontologies.

NuExtract demonstrates released small schema-conditioned generative extraction, including verbatim strings. But **NuExtract-2.0-4B is based on Qwen2.5-VL-3B and carries the Qwen Research License**, not the Apache Qwen3-4B dense model. Its weights/data lineage and multimodal architecture introduce unnecessary questions for this task. Use its typed output idea; do not silently substitute the model. [NuExtract model card](https://huggingface.co/numind/NuExtract-2.0-4B).

**Cost per message.** A realistic preliminary envelope is 300–1,200 input tokens and 40–200 output tokens, growing with rule count/register size. Working hypotheses for warm generation: 1.7B **0.5–4 s**, 4B **1–6 s**, 8B **2–10 s**, excluding queueing; measure p50/p95 and tokens, not just token rate. At 1–6 seconds, 4B consumes **0.00028–0.00167 GPU-hours/message**, or **0.28–1.67 GPU-hours/1,000 sequential messages**. These are budget estimates, not GB10 measurements. There is no API fee on this machine; marginal dollars require actual power/tariff measurements.

Base BF16 storage alone is approximately 3.4/8/16 GB for 1.7/4/8B; allow extra runtime/KV memory. A second vLLM instance needs an explicit memory allocation—two servers using default large memory fractions can collide. The small updater's request must finish before the renderer prepares the normal answer, so it adds latency on the critical path and competes with the trunk for bandwidth. Package-local HF inference is another route, with lower serving setup but potentially worse throughput. Base generation is protected by model separation, although wrong predicted writes can still alter its prompt and behavior.

## 6. C — Better discriminative extraction

**C1: DeBERTa-v3-large/ModernBERT-large + learned complete spans + target relations.** Use whole role/context/register input, multi-span start/end pairing or a sequence-constrained BIO head, span pooling, and relation scores against old-rule representations. Separate “no source rule” from “no change to this target.” Supervise quote-adoption evidence and persistence separately where annotations exist. A CRF can discourage internal O-gaps; it cannot conjure the 90 gold spans 44c never proposed. No more sentence splitter or post-hoc gap-merging rescue.

DeBERTa-v3-large has 304M backbone parameters plus ~131M embedding parameters; counting only the backbone understates residency. ModernBERT-large is ~395M and offers an 8,192-token context with a more efficient encoder architecture. These are plausible upgrades in semantic capacity/context, not published standing-rule detectors. [DeBERTa card](https://huggingface.co/microsoft/deberta-v3-large), [ModernBERT paper](https://arxiv.org/abs/2412.13663). bge-large-en-v1.5 is a convenient ~335M English embedding encoder, but its retrieval objective is not evidence of superior long-span boundary extraction; it needs token features and a supervised head, not just cosine similarity. [BGE card](https://huggingface.co/BAAI/bge-large-en-v1.5).

Joint extraction is established: SpERT trains entity spans and relations with transformer representations and strong negative samples. Reuse that joint objective idea for `(rule span, target version, operation)`; do not inherit short-entity width caps or assume that entity relations equal lifecycle operations. Cost can grow as number of candidate spans × register targets, so cap *supported input size* explicitly and count overflows as failures/abstentions, not silently truncate. [SpERT](https://arxiv.org/abs/1909.07755).

**C3: GLiNER-style or contrastive span learning.** GLiNER represents labels and candidate spans jointly and predicts multiple entities in parallel. That makes it a suitable architecture inspiration for multiple clauses, but a pretrained “instruction” label does not enforce our admission policy. [GLiNER, NAACL 2024](https://aclanthology.org/2024.naacl-long.300/). Original GLiNER-style span grids and the earlier GLiNER2 checkpoint can impose narrow width limits; the reuse memo records `max_width=8` for the latter. Expanding a grid raises cost and does not teach clause boundaries. Use boundary pairing with checked representability, or a cleared pretrained encoder with an original span head. [Reuse memo P1](reuse-research-astra.md).

NuNER uses LLM-annotated entity pretraining and contrastive representations; its few-shot results show the value of task-aligned representations. Reported average F1 rises from **39.37 at k=1 to 71.53 at k=64**, with different gains by dataset; these are few-shot NER scores, **not recall at 95% precision**. [NuNER, EMNLP 2024, Table 8](https://aclanthology.org/2024.emnlp-main.660/). Span-ConveRT is closer in interaction style: conversational pretraining supports low-resource dialogue span extraction and outperforms its compared general-purpose representations. [Span-ConveRT, ACL 2020](https://aclanthology.org/2020.acl-main.11/). Neither supplies a small-data result proving our precision-constrained recall bar.

For our data, contrasting independently authored direct rules with quote/report/non-adoption counterparts could teach the missing semantic distinction. Keep paired scenarios in one split. Joint span/target scores can also distinguish withdrawal+replacement from pure withdrawal after the spec is reconciled. Off-the-shelf checkpoint provenance remains a prerequisite: general encoder pretraining and downstream benchmark-supervised extraction weights are different lineage claims. Do not import GLiNER/NuNER benchmark fine-tunes merely because the architecture is useful.

**Runtime/package:** potentially no GPU inference cost when served on CPU. Local small-head p50 was ~51–88 ms; a larger encoder/joint head is provisionally **0.15–1 s/message CPU**, possibly longer with many targets, or **10–100 ms GPU** for short batches. These forecasts need measurement. It is a compact sidecar in one HF repo and cannot change trunk weights. It still needs grounded value extraction/normalization and transactional target binding to be a full updater. A cheap candidate gate that skips the generator is attractive only after demonstrating that its false negatives do not cap final recall below 85%.

## 7. D/E — Frozen prompting, better data, and learned memory policies

**D: finish check 46 before fitting.** Use schema-first definitions with precise label semantics, full authenticated message context, compact current register, explicit allowance for `[]`, and several independently authored examples that cover both multiple operations and no-op cases. Evidence-first output (`span` before operation fields) is a reasonable hypothesis; literal copying plus a substring/offset validator prevents fabricated evidence, but does not prove that the evidence is a binding instruction. Do not change the queued schema or prompt after reading evaluation results.

Use the current vLLM API: `structured_outputs={"json": schema}` (or the supported response-format JSON schema), not obsolete `guided_json`; the docs say the latter was removed in 0.12.0. **What do recent 30B-class studies actually establish?** MedStruct-S's two-shot 32B extraction remains far below its fitted counterpart (§3). LLMStructBench studies 22 model variants including Qwen3-32B; its summary reports Qwen3 4–32B around **0.65–0.69 micro F1**, with 32B not consistently ahead, and persistent value errors after structure improves. It is a prompting/structured-extraction study, not a matched few-shot standing-rule test or a proof of a ceiling. [LLMStructBench, 2026 preprint](https://arxiv.org/html/2602.14743v1). I found **no verified task-matched state-of-the-art result for frozen Qwen3-30B-A3B that licenses predicting both our bars**. Dense 32B, 30B-A3B MoE, OCR extraction and lifecycle reasoning are not interchangeable.

Chain-of-Verification drafts an answer, generates checks, answers checks independently and revises. Its factuality evidence motivates a DEV-only precision experiment, but it adds calls and is not an established cure for missed standing rules. [CoVe](https://arxiv.org/abs/2309.11495). Prefer deterministic evidence/target validation first. A self-judge agreeing with the extractor is not independent evidence; checking only emitted rules cannot discover omitted rules. Two-pass “find all candidates, then decide binding status” can be tested later with both costs charged, not slipped into check46's frozen one-call recipe.

**Local trunk latency anchor:** qualification measured **18.7 decode tokens/s** in one stream and **39.9 aggregate tokens/s** at concurrency four; first-prefill was ~823 tokens/s in that experiment. A rough unbatched 600-input/100-output updater is `600/823 + 100/18.7 ≈ 6.08 s`, before grammar/queue overhead. **E1: data coverage is the leading cross-cutting lever.** Prewrite authoring quotas and audit *actual* retained profiles. The 44c review proposes ≤50% cue-initial spans, ≥10% three-rule messages and ≥15% spans of ≤5 words as reopening conditions. Treat these as disclosed design choices motivated by exposed diagnostics, never as evidence of independent generalization. Obtain a fresh author-disjoint decision bank. Use multiple fit authors who see only the settled label spec and development-only illustrations; reserve a different author for validation. Kimi sessions alone are not author-disjoint. Specify positive/negative pairs for adopted quotes, terse task-local obligations, unchanged facts, unrelated additions and ambiguous targets. Add gold target distractors and complete operation lists. This is a better use of annotation effort than multiplying easy cue-heavy examples.

Self-Instruct supports generating and filtering synthetic supervision, but its recipe/data is not authorized fit material here. [Self-Instruct, ACL 2023](https://arxiv.org/abs/2212.10560). The local authoring contract specifically excludes template substitutions and paraphrase mills. Fresh model-authored, individually audited original scenarios are compatible with the existing approach; industrial template/teacher generation would require a prospective process change and new provenance controls. Estimate **4–12 person-hours for a targeted audit/coverage pass**, more for thousands of complete transitions; quality-auditing 10k new rows is not a one-hour task. CPU preparation uses 0 GPU-hours; local teacher generation could consume several GPU-hours and is outside these quick checks. More examples help only if they add the missing distinctions and clean full-state supervision.

**E2: hierarchy and prompt-update research.** Instruction Hierarchy teaches privileging authorized instructions over lower-trust content; Ghost Attention teaches persistence across turns. These inform role-preserving training cases, not our cancellation/reinstatement ontology. [Instruction Hierarchy](https://arxiv.org/abs/2404.13208), [Llama 2 §3.3](https://arxiv.org/pdf/2307.09288). Applying such training to the trunk's ordinary generation would expand the task; apply any new labels to the updater adapter only. A “system prompt optimizer” trained to improve downstream answers is also the wrong objective when immutable provenance and exact lifecycle changes are the requirement. Label/data integration is ~2–6 person-hours plus the chosen SFT cost, with no independently predictable accuracy gain.

**E3: learned write gates / memory RL.** SOM-DST predicts operations then generates only changed slot values; this is a useful hybrid architecture. [SOM-DST, ACL 2020](https://arxiv.org/abs/1911.03906). Mem-α learns memory construction using downstream QA reward, showing that write policies can be learned. But preserving answerable facts is different from rejecting quoted instructions and keeping exact version semantics. [Mem-α](https://arxiv.org/abs/2509.25911). Reuse a small operation gate if necessary; do not import a memory agent's pretrained write policy. Expect ~6–16 person-hours for gate/value integration and ~0.2–2 GPU-hours for a small supervised gate; complete rollout RL is likely >8 person-hours and >1 GPU-hour, with no useful task-matched accuracy estimate. A gate's FN rate can dominate end-to-end recall.

**E4: preference fitting / DPO.** Correct-vs-incorrect operation lists could target quote mistakes or spurious writes after SFT. DPO avoids a separate reward-model/PPO loop, but still needs clean preference pairs and reference-policy log probabilities. [DPO, NeurIPS 2023](https://arxiv.org/abs/2305.18290). We already have richer exact labels, so supervised likelihood is the first use of them. A preference reward that favors fewer writes can make precision look good by destroying recall. Budget ~4–8 person-hours for data/scorer integration, plus roughly SFT-scale or higher GPU cost; no established improvement over supervised fitting on our bars. Keep preference fitting off the trunk's base weights, and never construct preferences from benchmark outputs. This is outside the top three.
