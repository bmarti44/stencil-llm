**Inference:** the model often fails to interrupt a self-reinforcing wrong trajectory under these interfaces. It was never asked to rate alignment; its feedback was opaque, and old conflicting instructions remained visible. Neither “it knew but concealed it” nor “it cannot notice” follows. Detection, honest reporting, choosing a repair, and successfully executing that repair are four different measurements. A good successor probes the first wrong answer and the next recovery opportunity, preserving the episode as the statistical unit.

The literature therefore supports **closing some of the hidden-to-verbal reporting gap through training**, rather than guaranteeing its closure in this task. My narrower recommendation is to learn per-obligation probabilities of observable compliance, not a free-form “alignment score.” A score can be calibrated by always predicting the base rate and still be useless for deciding which response to inspect; require discrimination and selective risk as well as calibration. Good detection likewise need not improve repair.

Memory drift is empirically real; deliberate rationalization of one's own constraints is less directly established by these sources. [HaluMem](https://arxiv.org/abs/2511.03506) evaluates fabrication, errors, conflicts and omissions at memory operations, locating failures that end-to-end QA can hide. [MINJA](https://arxiv.org/abs/2503.03704) shows ordinary query interaction can induce malicious persistent records without direct database write access. These support the danger of feedback amplification and laundering untrusted content into memory, but do not establish spontaneous self-serving intent. [Wataoka et al.](https://arxiv.org/abs/2410.21819) find self-preference associated with familiarity/perplexity in LLM judging; that gives an additional reason to test grading one's own answers, not direct evidence of malicious register edits. I found no opened study certifying Brian's exact co-emitted, versioned-obligation system against rationalization. Treat that failure mechanism as a design risk to test, not a measured incidence rate.

**Safe architecture: proposals from the model, authority from outside it**

An illustrative transport is `answer` plus `proposed_ops[]` plus `ratings[]`. Each proposal carries `action, key, scope, kind, literal_value, source_message_id, source_span, target_version, base_register_hash`; the five actions are add/supersedes/cancels/completes/reinstates, with an empty list for no operation. The caller supplies authenticated source roles, task handles, event identities and evidence capabilities. The model cannot mint authority by outputting `role=user`, `adopted=true`, or a plausible receipt ID. Scope and request-kind applicability are separate from instruction kind. Global and task rules sharing a key must remain distinguishable.

1. Freeze the authoritative live view and applicable-obligation identifiers before the answer. Incorporate independently authorized current user events before this snapshot; if the current message is only unstructured prose, inferred events remain proposals. Give the model both the actual user message and existing register, never hidden gold operations. The answer must still address the user's new request.
2. Parse the side channel with a strict bounded schema. Resolve exact source offsets and literal values against authenticated messages; reject wrong role, quoted/payload-only origin, nonexistent task, cross-authority changes, ambiguous keys, stale versions, invalid reinstatement and duplicate/conflicting events. Grammar proves syntax only. **A verbatim span and valid user role do not prove adoption or correct interpretation of arbitrary prose.** Where adoption cannot be deterministically established from an explicit structured entry or an already authorized constrained interface, retain a suggestion for explicit adoption. Do not silently broaden the current authority contract.
3. Translate the proposal schema into the real typed API, then validate the entire transaction against its original register hash. This bridge is necessary: check48 retirement values are empty, while `Register._apply` requires the target value; check46 calls task-over-global a supersedes, while the register requires equal target scope. A task override normally adds a narrower rule while preserving the global one. Never copy the benchmark's supersedes operation into a global retirement. Freeze translation semantics and gold labels before the new fit.
4. A completion proposal needs an independently authenticated result tied to the exact task/version and completion criterion, or explicit authorized user closure. “I finished,” a high rating, successful syntax, and a related subtask's success are insufficient. The response being rated cannot complete away the obligation before it is graded. Ratings bind to answer bytes and the frozen obligation snapshot; subsequent valid state changes do not retroactively improve the score.
5. Only the external controller commits a validated transaction. Log proposed/rejected/committed operations separately, append version history, and fail closed on ambiguous authority. Use atomic durable state/journal semantics in a successor; FPR:112 documents that the current journal failure boundary is not sufficient. Do not change the running implementation.

This extends, rather than assumes away, the current boundary: `src/stencil/focus/loop.py:107` requires authenticated direct adoption and confirmed completion evidence; `src/stencil/focus/register.py:307` calls direct application a trusted structured API; at318–365 it checks authority, exact version, scope, reinstatement identity and pending completion. `results/quick-checks/check46/run.py:76` only parses/grounds extraction output and checks the one-rule target. It is not this authority validator. The pilot driver's completion receipts come from scheduled gold events (`scripts/composition_pilot5.py:131`), not independent verification of model work. A read-only canonical register plus a writable scratch-memory area is the sensible MemGPT/Letta-inspired division.

For the one-generation premise, answer-first then proposals/ratings lets the rating inspect the actual emitted answer and reduces direct conditioning of the answer on a proposed rule edit. It cannot let the answer consume a *validated* newly inferred register update in that same uninterrupted stream. If that is required, stop after proposing, validate externally, and resume decoding; call it an interrupted/two-stage generation and measure its cost. Never advertise both strict external validation before use and uninterrupted one-pass execution as if they were free.

**Carrier choice and verdict for Brian**

Structured side channels and fine-tuning solve different problems. A schema makes outputs parseable; a LoRA can improve the policy choosing their contents. Thinking tokens supply extra inference work, but are not an authenticated state store or an independent error signal. Start with a short explicit structured suffix and thinking disabled for a clean cost baseline; only test thinking as a separately budgeted matched ablation. MemReader supports trained reasoning-plus-tools, not “turn thinking on and trust the result.” Preserve full user/task context; do not trade away authority grounding to save tokens.

A single LoRA can in principle emit an answer and both side channels, but the opened literature and our checks do **not** establish non-degradation for that exact combination. Answer/proposal loss balancing and competent reference answers are sensible safeguards, not guarantees. Rating-only training on fixed answers isolates the easiest part but does not train the model to answer well. Adapter-OFF exact parity establishes reversibility on a matched computational path; it says nothing about ON competence or previously altered conversation history. Check40k is why the answer-quality control must be a gate, while check49 is why we should not declare trained carriers impossible.
