## Severity-graded findings

### HIGH 1 — the watchdog-pattern backstop is vacuous for normal multiline watchdogs

`tests/test_no_kill_patterns.py:27-29` reports a watchdog hit only when the literal word `watchdog` and a termination call occur on the **same source line**. A normal shape such as:

```python
def watchdog(process):
    while process.poll() is None:
        process.terminate()
```

recomputed to zero hits under the test's predicate. The repository contains the same split shape: `scripts/run_matrix.py:373-396` is `_watch_process`, which calls `_stop_process`; `scripts/run_matrix.py:364-370` invokes `process.terminate()` and then `process.kill()`. That existing launcher appears to manage its own child and may be a legitimate narrow exception, but it demonstrates that the new scanner cannot recognize the call structure. A rogue or accidental cross-process watchdog written in the same ordinary style passes the gate. The scoped suite did pass `tests/test_no_kill_patterns.py`, confirming the false negative is in the test, not merely hypothetical test failure.

This is HIGH because C3 specifically requires a mechanical regression gate against the watchdog class implicated in the prior breach. It is not elevated to critical: the project threat model is trusted-but-fallible, and static enforcement remains defense in depth rather than a same-UID sandbox.

**Required fix:** extract an AST-based/testable scanner that catches `terminate`, `kill`, `send_signal`, `os.kill`, name-based kill commands, and call-through from watcher loops/functions across lines. If caller-owned child termination in `scripts/run_matrix.py` remains permitted, encode it as a narrow audited allowlist exception rather than making the detector line-local. Add a synthetic multiline watchdog fixture that must produce a hit, plus a negative fixture for the explicitly allowed own-child path.

### MEDIUM 3 — `0444` is true in this worktree but is not reproducible from the commit

The current file passes the new check: mode is `0444`, and SHA-256 is `67ffeee0fcb87c317c5b08a2de85557b4a7e96ada6178aa645b4954fe4b53d49`, equal to `data/bench/pins-manifest.json:47` and asserted at `tests/test_sealed_guard.py:33-37`. ### MEDIUM 4 — common shell syntax bypasses process denial; deliberate indirection bypasses all four textual classes

Nominal literal cases are covered, but five decision-only probes (strings were inspected, never executed) produced:

| probe | guard result |
|---|---|
| `p=data/bench/ifeval_input_data; cat "${p}.jsonl"` | allowed |
| `command kill 123` | allowed |
| `p=python; $p -c 'import torch'` with simulated busy PID 999 | allowed |
| `EMPTY=; no${EMPTY}hup python cpu_job.py` with `STENCIL_SUBAGENT=1` | allowed |
| `kill -9 123` with owned PID set `{123}` | denied (signal number `9` is misread as a target PID) |

The direct `command kill` bypass and numeric-signal false positive violate the stated process-control contract without requiring encoding or `eval`; those make this MEDIUM. Variable splitting illustrates the unavoidable lower-assurance boundary of a text guard and is not graded high/critical. The implementation itself acknowledges none of this boundary at `tools/hooks/pretool_guard.py:62-80`, `:83-96`, and `:109-140`.

**Required fix:** recognize `command` and option-bearing `sudo`/`env`/`xargs` command positions, parse `kill` signal options separately from target PIDs, and add these two cases to the table. Add explicit documentation/tests showing that variable expansion, command substitution, encoded payloads, nested shells, and equivalent APIs are out of scope; rely on entry-script GPU ownership checks, sealed hashes/mode, and code review as the stronger layers.
