## Four stages, at most one correction barrier

Use the accepted staged construction shape: one complete source scaffold and
three reference/check packets per project. The initial module, complete source
schedule, target names and generic current requests become immutable once the
scaffold is validated. All prior accepted packets are immutable. The same-project
future source schedule remains visible for check expiry, but current references
and expectations may use only the prefix through the current round. Independent
semantic review must still check that distinction.

Four ordinary stages have at most four concurrent author calls each. Stage 0
failure stops the bank. HTTP, envelope, malformed inner JSON, structural schema,
deadline or unexpected local failures stop the bank; they never cause a retry.
Only structurally valid stages 1–3 packets that raise StageValidationError from
reference action rejection, failed active reference checks, mutant action
rejection or failure to demonstrate the designated retirement can use the single
correction barrier. Structural ValueError and all other failures remain terminal.

StageValidationError alone is insufficient: the reused run_checks also records
local failures as check errors. Examine every available public/private/mutant
result before deciding correction eligibility. Error must be null or exactly
"InvalidProgram: " followed by one of these fixed labels: AttributeError,
TypeError, ValueError, KeyError, IndexError, NameError, UnboundLocalError,
ZeroDivisionError, OverflowError, RecursionError, AssertionError, RuntimeError,
StopIteration. Any other error string makes the bank INCOMPLETE with no correction.
In particular sandbox deadline/resource failure, resource bound, MemoryError,
setup/process/JSON failures and unknown outer exceptions are terminal. Request,
whole-job and between-check deadlines are always terminal. This rule takes
precedence over the ordinary StageValidationError handling, including when the
global correction allowance is still unused.

This is a boundary on observable recorded errors, not perfect cause diagnosis:
an opaque sandbox ValueError label can represent more than one internal cause.
The whitelist deliberately permits that label while excluding unrecognized or
path-bearing local exception text. No new sandbox/error framework is required.

After all independent calls and validations at that ordinary stage finish:

1. If any failure is outside the correction boundary, stop the bank.
2. If one or more eligible failures occur and the global allowance is unused,
   consume it once and request one corrected packet for each failing project,
   at most four calls concurrently. Do not call successful siblings again.
3. Each correction receives only its own frozen scaffold, prior accepted packets,
   original current packet and the fixed diagnostics projection below. No other
   project, scientific worker output, hidden selected-source target or proposed
   human repair is supplied. Kimi is the sole correction author.
4. Preserve the original current packet's public/private check-ID sets and their
   partition exactly. Also preserve each check's symbol, source_ids, behavior,
   active_from_round and active_through_round, and the final mutant's
   failing_check_id. No failed check or its coverage role may disappear. Only
   reference_patch, each check's input/expected_values/rationale and the mutant's
   source may change. Every changed value must still follow the frozen sources;
   prior accepted checks cannot change. Preserve exact original/corrected packets
   and their structural differences for independent semantic review.
5. Validate a corrected packet through the same actual consumer, starting from
   the unchanged pre-round reference module, with all active prior checks. The
   failed attempt's reference is not an accepted workspace state. Do not reapply
   successful siblings' references. A failed correction ends the bank.
6. Continue ordinary stages only when all four projects at this stage validate.
   A later failure ends the bank because the global correction allowance is spent.

There is no second correction, source rewrite, project replacement, hand edit,
reduced-bank score, repeat batch or worker-answer-driven tuning. Final independent
source-semantic rejection also stops the bank; it grants no further correction.

## Correction request and registration

Use the unchanged scaffold-prompt.txt and round-prompt.txt from the accepted
source-replay-staged directory. Their ordinary rendering stays unchanged except
that data_contract is this registration's DATA-CONTRACT.md, the inherited exact
contract followed by an explicit description of the existing single-value call.
Use this directory's correction-prompt.txt for the one allowed correction.

Its exact one-pass string.Template placeholders are project_id (JSON string),
round_index (decimal integer), scaffold (public scaffold JSON), prior_packets
(accepted same-project packet array), original_packet (the failed current packet
JSON), diagnostics (the projection below), and data_contract (exact new contract
text). JSON rendering stays ensure_ascii=false, allow_nan=false, sort_keys=true,
compact comma/colon separators; inserted values are never parsed as templates.

Diagnostics has exactly {code, failed_checks}. Code is one of
REFERENCE_ACTION_REJECTED, REFERENCE_ACTIVE_CHECK_FAILURE,
MUTANT_ACTION_REJECTED, MUTANT_DESIGNATED_CHECK_NOT_FAILED.
For an active-reference failure, failed_checks contains only failing result
records, ordered public then private as in actual validation. Each has exactly
{check_id, passed, actual, error}, copied from that construction execution.
For a mutant that did not fail, it contains the designated mutant result (which
may have passed). Only null or the eligible exact error labels above may appear.
For action rejection it is empty. Never include whole execution
records, module text, timing, internal paths, sibling data or worker answers.

Actual values and short recorded error strings here come solely from running
Kimi's own construction reference against its own checks. They are permitted
construction feedback, not evaluated coding-worker answers. Sol suggested using
only diagnostic codes; root instead permits this narrow result projection to
make automated correction useful. Independent review must assess that choice.
These fields cannot be used to fit or select the scientific selector/worker.

Keep the CLI shape --run-dir --freeze --execute. New results, canonical review,
immutable preparation-code-review-at-acceptance.md snapshot, preparation-freeze.json
and the exclusively new preparation-run-01 live in this directory. Shared code
changes are versioned and independently re-reviewed; historical launch commits
remain their exact implementation evidence. Historical data/documents/reviews/
freezes and qualified helper files are not overwritten or silently rebound.

The new freeze binds this PREPARATION.md, this DATA-CONTRACT.md, this correction

## Bounds and evidence

At most 16 ordinary plus 4 correction requests: 20 total. Reserve all planned
ordinary and correction slots before the first call; unused correction slots
remain explicitly unattempted. The correction slots must bind the actual triggering
round without creating extra per-round allowances. Requests use the same existing
local Ollama Kimi alias, normal nonstreaming thinking mode and exact reviewed
renderers. There is no provider, package, model or data download.

Keep the 450-second request maximum and 2400-second whole active preparation
ceiling if the final implementation supports the declared bound. Five worst-case
HTTP waves use 5 x 450 = 2250 seconds, leaving a nominal 150 seconds for validation,
assembly and publication. This arithmetic is not a completion forecast; the
absolute whole deadline dominates and a late result remains incomplete.
Review time is separately reported. No additional call or budget is permitted
merely because the original requests happened to finish quickly.

Freeze exact new specification/prompts, reviewed code and immutable review
snapshot before authorship. Preserve the same strict raw evidence, attempt counts,
owned-process cleanup and terminal handling. Use a small registration change to
reuse the accepted tool; do not copy another entire runner or add a review parser.
Sol's read-only assessment found this narrow reuse feasible; code acceptance
remains required before any call.

After construction, independent Astra review must assess all source/check/reference
semantics and every corrected value against frozen instructions. Then accept the
actual scientific runner and new bindings, run its final CPU/token/cost preflight,
and freeze a launch only if every registered prerequisite passes. The earlier
technical qualification is not rerun. A small screen pass can authorize larger
fresh validation; it cannot complete the project goal.
