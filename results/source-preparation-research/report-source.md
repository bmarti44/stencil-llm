## What the evaluation literature supports

EvoCode-Bench distinguishes terse follow-ups using prior conversation and
repository state from detailed specifications repeated each round. Its references
execute sequentially; cumulative behavioral tests preserve active requirements
and replace superseded assertions. Review checks whether assertions follow
instructions and alternative correct implementations can pass. This supports
staged executable validation and realistic persistent code. Its engineers and
reviewers also revise task material; the paper does not prove a fully automatic
authoring pipeline. We adopt validation principles, not its benchmarks, fail-stop
scoring or data-repair process. [Shen et al., EvoCode-Bench, v1, 22 May 2026,
§§3.1–3.2/B.4–B.5](https://arxiv.org/html/2605.24110v1).

LLMs Get Lost In Multi-Turn Conversation separates progressive disclosure from
concatenated instructions and repeated recaps. A generic request preceded by all
necessary rules can still resemble a recap. Its shards are intentionally
order-insensitive, unlike evolving requirements; its preparation also includes
manual inspection and editing. Neither its construction nor its outcome numbers
establish local coding-focus performance. [Laban et al., v1, 9 May 2025,
§3.3/§7.1/Appendices B–C/M](https://arxiv.org/html/2505.06120v1).

CodeFlowBench explicitly conditions each round on the current function signature,
current specification, previous code and overarching background. Thus meaningful
multi-turn coding does not by itself measure recall of older instruction text.
Its dependency-based decomposition is not needed here. [Wang et al., CodeFlowBench,
v4, 15 April 2026, §3.3](https://arxiv.org/html/2504.21751v4).

## Small prospective change

Use four fixed stages per project, at most sixteen authoring calls for the whole
new four-project bank. This is a proposal to register before any generation:

1. Kimi authors the initial module, project description, twelve source-message
   texts and three target names. Freeze this complete public schedule before
   generating tests. A deterministic assembler supplies IDs, roles, fixed path,
   envelope fields and one generic action-request template with the target name.
   It does not write or summarize substantive requirements.
2. Three sequential Kimi calls each author one round's reference patch and new
   public/private checks. The final call also authors the obsolete-rule mutant.
   Each receives only its own immutable project schedule and earlier accepted
   author artifacts, never another project, a worker response or failure feedback.
3. Validate structure and execute that round's reference against all currently
   active checks before spending on the next dependent call. Assemble the exact
   existing public/private project schema; no semantic rewriting during assembly.
   A failed stage stops the proposed bank; no correction calls, substitute cases
   or repeated batches are implied. Already launched independent calls may finish
   for their records; do not start subsequent stages after a known bank failure.
4. Review source/test/reference agreement independently and perform the final
   actual consumer preflight and bindings before any coding-worker exposure.

The call count and no-repair boundary are engineering choices to bound this next
attempt, not claims from the papers or retroactive changes to the failed attempt.
The new specification must freeze exact prompts, stage schemas, request template,
local validation order, budgets and whole-bank stopping semantics. Root does not
hand-author task answers. Kimi remains the substantive data author.

Check expiry requires knowing the complete future schedule: a round-one author
must decide when a check stops applying. All round authors therefore see the
frozen schedule, but expected behavior and references must follow only sources
visible through their round. Prefix-limited source IDs are necessary, insufficient
evidence of that semantic restriction; independent review must catch future-rule
leakage. Do not infer intervals with regexes or silently expire old tests.

Fixed requests prevent a generated request from becoming a full rule recap; they
do not prove a need to recall older history. They also change communication style
prospectively, so no result can be pooled with the stopped bank. Review should
describe where relevant behavior is specified: current request, nearby messages,
older messages and existing code. Preserve realistic code and all authentic
history; do not demand that every requirement be absent from code or require the
baseline to fail. Nearby recaps limit attribution to long-term selection; retain
the recent-source control to measure that possibility rather than moving the
goalposts or selecting a new control winner afterward.
