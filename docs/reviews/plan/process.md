## Findings

1. **High — A review can pass the wrapper while high or critical findings remain open.** Section 2b's “Resolution rule” requires that “Work is accepted only when zero high/critical findings remain open and the review score meets the threshold” (`PLAN.md:93`). The actual terminal check only parses `**Score:**` and returns success when `score >= args.threshold`; it never parses finding severities or statuses (`tools/check_review_scores.py:18`, `tools/check_review_scores.py:51-64`), and the review wrapper delegates its final exit solely to that check (`tools/run_codex_review.sh:343`). This is the exact silent-drop path the plan says must not exist. It also creates score/status ambiguity: the review template hard-codes “PASS (≥90)” (`tools/codex-prompts/_common-header.md:13`) while the wrapper accepts an arbitrary positional `threshold` (`tools/run_codex_review.sh:27-34`), so a non-90 threshold can make the displayed verdict disagree with the wrapper result.

2. **High — The claimed append-only review history is not enforced and can be deleted wholesale.** Section 2b says “Round logs are append-only” (`PLAN.md:92`). The validator explicitly says it “replaces the strict append-only validator with a softer contract” (`tools/review_round_tracking.py:1-9`) and validates only the presence and shape of the new round (`tools/review_round_tracking.py:76-95`); it never checks that any prior round remains. The wrapper likewise says “We no longer enforce strict byte-identity on prior rounds” (`tools/run_codex_review.sh:271-277`). A later reviewer can therefore remove the round that contained an unresolved high finding and still pass validation, destroying the only durable audit trail.

3. **High — Refutation is unilateral and has no durable finding identity or reviewer concurrence requirement.** Section 2b allows the orchestrator to “refute[] it with recorded evidence in the review file and ledger” after it “independently verifies every high and critical finding” (`PLAN.md:93`). It does not require the reviewer to accept the refutation in a subsequent round, define who may edit the reviewer-owned canonical file, assign immutable finding IDs, or preserve a status-transition record. The ledger only asks for prose “findings or results (with severity for review findings and their open/resolved/refuted status)” (`PLAN.md:103`). Combined with Finding 2, an orchestrator can self-refute, omit the finding from current findings, and accept the work without an adversarial adjudication.

4. **High — The ledger cannot deliver its stated cold-start guarantee or survive an abrupt interruption.** The Work log promises that “a restarted session must be able to resume from this file alone” (`PLAN.md:101`), but its triggers occur after “completing a work unit,” “finishing a review round,” or “ending a session with work in flight” (`PLAN.md:103`). A crash or forced restart executes none of those triggers. Required state is also absent: work-unit ID and state, phase/gate, branch and HEAD SHA, dirty paths, brief path/hash, Codex session/process ID, command and log path, model/effort, test command/result, artifact/config/run IDs, matrix cells planned/running/completed/failed, checkpoint, retry count, blockers, and open finding IDs. The live entry merely says “Launched sol@xhigh adversarial review ... Findings: pending” (`PLAN.md:107`), which is not enough to discover or reconcile in-flight processes or partially written artifacts.

5. **High — Threshold pre-registration is internally contradictory and presently has no tamper-evident baseline.** Operating rule 3 says thresholds “change only by human edit to this file before the phase's runs begin” (`PLAN.md:70`), while Appendix C says “Editing them after Phase 3 begins requires a human commit to this file with a rationale line” (`PLAN.md:415`), which expressly permits the edit at the time rule 3 forbids it. No trigger records when a phase or individual run began, “human” is not authenticated, and the Amendment log is mutable prose (`PLAN.md:7-12`) with no commit SHA, approver identity, old/new value, or signed hash. README nevertheless claims “every pass bar was frozen before any experiment ran” (`README.md:41`). `git status --porcelain=v1` on 2026-08-22 showed `PLAN.md`, `README.md`, and `tools/` as untracked and `git log` contained only the initial LICENSE/.gitignore commit, so there is not yet a repository object against which a post-hoc edit could be detected.

6. **High — Rule 4 is impossible to follow for five of the six gates.** Operating rule 4 says, “On any gate failure, execute the decision tree in Appendix D” (`PLAN.md:71`), but Appendix D is titled “Root-cause tree for G3 failures” and contains only G3 branches (`PLAN.md:430-437`). G0, G1, G2, G4, and G6 have no defined red state, retry budget, escalation, kill/continue decision, or required ledger/README transition. An agent can either invent a procedure in violation of rule 7 or ignore rule 4; Phase 6 is especially open-ended because its only stated exit is “green, commit” (`PLAN.md:377-382`).

7. **High — The G3 fallback authorizes proceeding while the written gate remains red.** Phase 3 first requires “G3.1 through G3.4 ... green” but in the same exit paragraph says, “If G3.2 fails, run Appendix D, then either fix a diagnosed defect, proceed with M1b as primary per D.3, or kill” (`PLAN.md:348`). Appendix D.3 likewise says “If M1 still fails ... designate M1b the primary variant, and continue the plan” (`PLAN.md:436`), while the kill criterion says a failed G3 stops except for that exception (`PLAN.md:62`). There is no replacement definition such as G3.2-waived, no amended gate result, and no README status value for “continued with a failed clause.” This lets an agent call G3 green and make a `gate(G3)` commit even though the pre-registered G3.2 condition is false.

8. **High — Gate, review, commit, and README state are related by prose but not one atomic acceptance rule.** Rule 5 says, “One commit per green gate” and that the commit “also flips the corresponding row” (`PLAN.md:72`). Section 2b separately says a review occurs “before its gate commit” and that review score cannot substitute for a scientific gate (`PLAN.md:94`). Nothing defines a single checklist requiring green gate evidence, all required topic reviews at threshold, zero open high/critical IDs, ledger update, and README update before the commit is created. README's table stores only `not started` (`README.md:44-57`), with no allowed states, evidence path, review score/round, commit SHA, date, or failed/waived/killed representation. A green test result can therefore be committed and shown as complete while review acceptance is red.

9. **High — The drift-containment implementation can overwrite concurrent work and still succeeds on uncontained drift.** Section 2b mandates, “Drift outside that is restored and reported” (`PLAN.md:95`). The wrapper snapshots dirty files and later blindly copies the snapshot over every still-dirty non-review path (`tools/run_codex_review.sh:299-325`); it cannot distinguish a reviewer's mutation from a coder's legitimate concurrent update after the snapshot. Conversely, it explicitly leaves newly dirty files untouched (`tools/run_codex_review.sh:327-332`), swallows the allowlist check with `|| true` (`tools/run_codex_review.sh:293-296`), and proceeds to the score check. The message still says “drift contained” (`tools/run_codex_review.sh:338-343`). Under the stated multi-session execution model, this can both erase in-flight changes and return success after out-of-scope changes survive.

10. **High — The orchestrator's direct-edit exception contradicts the fixed role boundary and TDD chain of custody.** The fixed role says the orchestrator “does not write implementation code directly,” and the coder “Writes all implementation code and tests” (`PLAN.md:85-86`); rule 9 repeats “All implementation code is written by sol” (`PLAN.md:76`). The resolution rule nevertheless allows “fix via a coder round or direct minimal edit” by the orchestrator (`PLAN.md:93`). “Minimal” is undefined, no test-first requirement is attached to that path, and no independent coder provenance is required, so a high finding can be patched outside the mandated coder/TDD workflow.

11. **Medium — Coder briefs and fixed model provenance are assertions, not enforceable contracts.** Section 2b specifies only “a brief in `tools/codex-agents/<name>.md`” and says coders write within scope (`PLAN.md:86`, `PLAN.md:95`); it does not require fields for objective, allowed paths, forbidden paths, dependencies, acceptance tests, prior findings, gate, output artifacts, stop conditions, or ledger handoff. The coder launcher uses sandbox bypass (`tools/run_codex_agent.sh:40-47`) and has no post-run diff allowlist. It also documents and implements `CODEX_MODEL` / `CODEX_EFFORT` overrides (`tools/run_codex_agent.sh:7-10`, `tools/run_codex_agent.sh:44-45`) despite the “Roles, fixed” model/effort claim (`PLAN.md:83-87`), with no required provenance record.

12. **High — Phase 5 and Phase 7 can escape review, and Phase 6 can bypass Phase 5.** Review cadence is “at minimum one review per phase before its gate commit” (`PLAN.md:94`), but Phase 5 explicitly has “No pass/fail gate” and only commits `tradeoff.md` (`PLAN.md:362-366`), while Phase 7 has no gate or exit review at all (`PLAN.md:384-386`). Phase 6 says it is “Only reached with G3 and G4 green” (`PLAN.md:368-370`), not with Phase 5 complete and reviewed. A literal agent may skip the H2 switching deliverable, run Phase 6, and finish the report without adversarial review of either Phase 5 or the final claims.

13. **High — The compute budgets are not executable budgets on the named single device.** Phase 3 fixes 20k steps, batch 64, and fp32 (`PLAN.md:330-337`); the enumerated matrix is exactly 90 runs and Task A alone processes about 107 billion token positions before Task M, yet the only schedule is “a weekend ... worst case” (`PLAN.md:337`) with no measured steps/sec pilot, maximum aggregate GPU-hours, checkpoint cadence, run timeout, resume rule, or prioritization. Phase 6 is worse: “day-scale runs” and “If a single run exceeds 48h wall clock, halve tokens” (`PLAN.md:372-375`) never define the original token count, number of seeds, optimizer schedule, corpus split, evaluation cadence, or whether both paired variants must be reduced identically. NVIDIA documents the Spark's headline 1 PFLOP only for sparse FP4 and 273 GB/s memory bandwidth; that headline does not validate this plan's fp32/bf16 training estimate. The budget therefore cannot drive a cold-start decision or prevent an open-ended matrix.

14. **Medium — The global determinism rule conflicts with the Phase 6 exception.** Rule 6 states, “Any change that breaks the determinism test (Section 3) is a regression, full stop” (`PLAN.md:73`), and Section 3 says “Every training or eval entrypoint must satisfy” its contract (`PLAN.md:111-119`). Phase 6 then says “bf16 permitted, determinism relaxed to seed-logged (bitwise not required at this phase)” (`PLAN.md:374`). The plan does not split the test suite into toy/proof and scale contracts or say which `make verify` result governs a Phase 6 commit, so both obeying and violating the bitwise test can be rationalized.

15. **Low — The governed README contains status-adjacent claims that do not match the gate semantics.** README says the normal model “fails every time, guaranteed” (`README.md:17`) and calls the baseline threshold “coin-flip level” (`README.md:33`). PLAN defines chance as 1/16 (`PLAN.md:258-259`) and accepts up to 8.25% (`PLAN.md:419`), so neither “every time” nor “coin-flip” is accurate. Because README is declared a governed artifact whose disagreement is “a bug” (`PLAN.md:157`), these are not harmless copy edits; they weaken the reliability of the explanatory status surface.

## Recommendations

1. Replace the score-only acceptance check with one command that validates the configured threshold, verdict consistency, current open finding IDs/severities, required review topics, scientific gate evidence, ledger update, and README row before permitting a gate commit (`PLAN.md:72`, `PLAN.md:93-95`; `tools/check_review_scores.py:18-64`). Reject thresholds outside 0-100 and derive the displayed verdict from the supplied threshold.
2. Restore strict round preservation: require every prior `### Round N` block byte-for-byte unless a separately logged correction is explicitly allowed, require monotonically increasing unique rounds, and fail if any prior high/critical finding ID disappears without a later reviewer-authored closure (`PLAN.md:92`; `tools/review_round_tracking.py:1-95`).
3. Give every finding an immutable ID and append-only state transitions (`open -> resolved` or `open -> refuted`). Require a fresh reviewer round to accept refutation evidence before acceptance; the orchestrator must not edit reviewer-authored history (`PLAN.md:93`, `PLAN.md:103`).
4. Replace the free-form ledger entry with a required schema containing phase, gate, work-unit ID/state, actor/session ID, branch/HEAD, dirty paths, brief hash, PID/job ID, command/log, model/effort, test and artifact/run IDs, matrix manifest/checkpoint, finding IDs, blockers, and exact next command. Add write-ahead triggers before launching an agent/run and checkpoint triggers after each matrix cell, not only orderly session-end triggers (`PLAN.md:99-107`).
5. Reconcile rule 3 and Appendix C into one immutable policy. Before Phase 0, commit a human-approved baseline containing a hash of the threshold table; record `phase_started_at` and first-run IDs in the ledger; after that point require a signed amendment with old/new values, rationale, affected hypotheses, invalidated runs, and mandatory rerun scope (`PLAN.md:7-12`, `PLAN.md:70`, `PLAN.md:413-428`).
6. Create an explicit red-state procedure for G0/G1/G2/G4/G6 with retry limits, allowed diagnostics, ledger/README state, escalation, and stop criteria. Restrict Appendix D by changing rule 4 to G3 only or supply per-gate trees (`PLAN.md:71`, `PLAN.md:287-382`, `PLAN.md:430-437`).
7. Make D.3 a formal pre-registered alternate outcome: define whether G3 is `green-with-M1b-primary`, `waived`, or red; state which clauses are replaced; forbid reporting G3.2 as passed; and encode that state in README and the ledger (`PLAN.md:62`, `PLAN.md:339-348`, `PLAN.md:436`).
8. Define a machine-checkable gate manifest and atomic commit precondition. README rows should use a controlled state enum (`not-started`, `in-progress`, `red`, `green`, `waived`, `killed`) and include evidence path, required review files/rounds/scores, finding-closure check, date, and gate commit SHA (`PLAN.md:72`, `PLAN.md:94`, `README.md:44-57`).
9. Remove blind restoration from concurrent worktrees. Run each coder/reviewer in an isolated git worktree or serialize with a lock; make any diff violation a hard failure; report exact paths; and never claim containment for paths left modified (`PLAN.md:95`; `tools/run_codex_review.sh:293-343`).
10. Delete the orchestrator “direct minimal edit” exception or narrowly define it as non-implementation documentation only. All code/test fixes should receive a scoped coder brief, TDD evidence, diff validation, and a fresh review (`PLAN.md:68`, `PLAN.md:76`, `PLAN.md:83-93`).
11. Define and validate a coder-brief schema and an allowed-path manifest. Pin model and effort in the launcher or record every authorized override with approver and reason in the ledger; add coder diff enforcement comparable to, but safer than, reviewer enforcement (`PLAN.md:83-95`; `tools/run_codex_agent.sh:7-16`, `tools/run_codex_agent.sh:40-47`).
12. Require reviews before every phase exit artifact, including Phase 5 and Phase 7, and make Phase 5 completion/review an explicit prerequisite for Phase 6. Define the final acceptance gate for REPORT.md (`PLAN.md:94`, `PLAN.md:362-386`).
13. Add a short benchmark phase on the actual Spark, publish measured tokens/sec and peak memory by sequence length/variant, derive per-cell and aggregate GPU-hour budgets, and define checkpoint/resume/timeouts. Freeze Phase 6 tokens, seeds, corpus/split, steps, and paired-reduction rule before it starts (`PLAN.md:330-337`, `PLAN.md:368-380`).
14. Split determinism into named `toy-proof` and `scale` contracts and state exactly which tests each gate runs. Keep proof tests bitwise fp32 while defining repeatability tolerances and evidence for bf16 scale runs (`PLAN.md:73`, `PLAN.md:111-121`, `PLAN.md:374`).
15. Correct README's “fails every time” and “coin-flip” language to “cannot exceed 1/16 chance in expectation; gate tolerance 8.25%,” and add a validation test that checks governed gate/status facts against PLAN (`README.md:17`, `README.md:33`, `PLAN.md:157`, `PLAN.md:258-259`, `PLAN.md:419`).
