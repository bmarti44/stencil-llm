## 2b. Execution toolchain and adversarial review protocol (added v1.3)

Roles, fixed:

- Orchestrator: the Claude Code session driving this plan. It decomposes phases into work units, writes briefs, launches sol, verifies review findings, resolves what must be resolved, maintains this file's ledger, and makes gate/commit decisions. It does not write implementation code directly.
- Coder: the Codex CLI (`codex exec`) running model `gpt-5.6-sol` at `model_reasoning_effort=medium`, invoked via `tools/run_codex_agent.sh` with a brief in `tools/codex-agents/<name>.md`. Writes all implementation code and tests, following TDD per rule 1.
- Reviewer: the same model at `model_reasoning_effort=xhigh`, invoked via `tools/run_codex_review.sh <phase> <topic> <threshold>`. Performs adversarial review of the work, scored 0 to 100, writing to `plan/reviews/<phase>/<topic>.md`.

Review protocol:

1. Every review is adversarial: the reviewer's job is to break the work, not to bless it. Findings are graded low / medium / high / critical.
2. Context carry-over: each review round's prompt includes the prior rounds' full review file verbatim (the wrapper does this), so the reviewer always sees what it previously found, what was claimed fixed, and scores the delta. Round history is append-only in exactly this enforced sense (aligned v1.7): round headings and their recorded Score lines are immutable, high/critical findings may be closed with markers but never vanish, and any other change to prior content MUST carry a dated `(updated ...)` annotation — unannotated silent edits are a protocol violation the next round's reviewer is instructed to flag. `tools/review_round_tracking.py` enforces the mechanical invariants; the annotation duty binds the reviewer.
3. Finding identity and closure: a finding's identity is `<topic>#<number>` and its number is stable across rounds. The orchestrator independently verifies every high and critical finding (reads the code, reruns the test, or reproduces the claim), then either fixes it or prepares a refutation with evidence. Closure requires reviewer concurrence: only a subsequent reviewer round may mark a finding `(resolved ...)` or `(refuted ...)` after checking the fix or the refutation evidence itself; the orchestrator never edits reviewer-authored review files. `tools/check_review_scores.py` treats any unmarked high/critical finding as open and fails regardless of score. A human may override a deadlocked finding; the override is recorded in the ledger with rationale.
4. Resolution scope: fixes to implementation code and tests go through a coder brief (TDD per rule 1). Every coder brief MUST ship a scope allowlist `tools/codex-agents/<name>.allow` (glob patterns, one per line); the wrapper refuses to launch without one and hard-fails on out-of-scope diffs (mandatory per tie-break batch 2, 2026-08-22). A failed coder run's partial work is preserved as diagnostic evidence, never auto-reverted (same tie-break). Brief contract (v1.13, provenance v1.18): every brief states the objective, the allowlist, the tests to write first, the acceptance command, and the ledger handoff; the handoff entry MUST record the model, effort, wrapper log path, and codex session id actually used, and any CODEX_MODEL/CODEX_EFFORT override requires a ledgered reason. The orchestrator may directly edit only non-implementation files: PLAN.md, the plan/ working directory (PROTOCOL.md, LEDGER.md, AMENDMENTS.md), README.md, AGENTS.md, CLAUDE.md, configs, docs, and process tooling under tools/ (allowlist made explicit for the v1.17 split). Work is accepted only when zero high/critical findings remain open and the review score meets the threshold (default 90). Medium and low findings are recorded in the ledger and may be deferred with a stated reason.
5. Cadence: at minimum one review per phase before its exit commit. Lens selection, adaptive (v1.13, human directive): the orchestrator examines the work unit's actual diff and writes a purpose-built rubric fragment `tools/codex-prompts/review-<slug>.md`, where `<slug>` is the review's canonical topic identity: chosen once at first launch, recorded in the write-ahead entry, and reused verbatim for every later round of that review (v1.18) through whatever lens is most likely to break that change (numerical-analysis for cell math, distributional/leakage for generators, equivalence for refactors, claims-vs-evidence for writeups — or several fragments when the diff warrants); the chosen lens and rationale go in the write-ahead ledger entry, and lens adequacy is audited at retros against escaped defects. `review-phase.md` is the fallback when no bespoke lens is warranted, and the phase's kimi cross-review ALWAYS runs the generic `review-phase.md` lens regardless of bespoke sol lenses — the coverage backstop ensuring no diff is reviewed only through orchestrator-chosen lenses (v1.14). Known kimi coverage limits, disclosed rather than implied away (v1.18): kimi sees text artifacts only (no figures/binaries — their absence is stated in its context header) and oversized files are skipped with an explicit marker; amendments use `review-amendment.md`; retros use `review-retro.md` (kimi). Tie-breaks run via `tools/run_tiebreak.py` (prompt committed first, raw response preserved). One review (one canonical file, whatever its lens) still holds one reviewer session across its rounds. Topic manifest (v1.22, closes process#36): each phase's registered reviews live in `plan/reviews/<phase>/topics.txt`, one topic per line, a line reading `<topic> kimi` when a kimi companion (`<topic>-kimi.md`) is required; the manifest is written in the phase's first write-ahead entry and thereafter append-only; both wrappers refuse a topic absent from an existing manifest, and acceptance validates codex files against it and requires every flagged kimi companion. Required gate artifacts may be listed in `plan/reviews/<phase>/artifacts.txt`; the kimi context manifest reports each one present or absent, with byte size and sha256 for PRESENT rows; PRESENT rows for BINARY artifacts must additionally carry a prose description sufficient for content review — hash and size alone do not satisfy presentation — with enforcement binding at the first PRESENT binary row (batch-5 UPHOLD, 2026-08-22). Process #29 is deferred-open until that first row exists, not complete. Plus a review of any change to this file's governed content (hypotheses, thresholds, architecture). Plan-phase acceptance, defined (v1.12): the plan itself is accepted when `tools/check_acceptance.sh plan` passes — all sol plan topics at 90+ with zero open high/critical findings and kimi cross-reviews on file — after which Phase 0 may begin and further plan changes follow the amendment path. The gate's own tests (Appendix C) remain the scientific pass/fail authority; review scores gate code quality and cannot substitute for a green gate, and vice versa.
6. Gate acceptance checklist, all items required before a gate commit: (a) gate tests green (or the exact registered qualified state recorded), (b) the phase's sol review accepted, verified by `tools/check_acceptance.sh <phase>` (thresholds hardcoded at 90 inside the script — not parameterizable at invocation, v1.10), (c) the phase's kimi cross-review run before the commit with its confirmed high/critical findings resolved (v1.7), (d) ledger entry written, (e) README status row updated, (f) commit message names the gate state. No item may be waived by the agent.
7. The wrappers' file-write policy is mandatory: reviewers write only their canonical review file; coders write only what their brief scopes. Uncontained drift is a hard wrapper failure, not a warning. Wrapper runs are serialized per repo via `.review.lock`; never run a coder and a reviewer concurrently in this repo, and never edit repo files while a wrapper is running (its drift restorer will clobber the edits).
8. Budget discipline: before launching any multi-run matrix, run one pilot cell, record measured steps/sec and peak memory in the ledger, derive per-run and total wall-clock estimates, and set each run's timeout to 4x its pilot estimate. A matrix projected within 2x the phase's stated budget may launch with the projection recorded in the ledger; beyond 2x, pause for the human.

Purpose-scoped review and stop-loss (v1.23, human ruling — Adjudication 3). THREAT MODEL, registered: agents are trusted-but-fallible; enforcement tooling detects mistakes and is NOT a defense against a malicious same-uid agent (unattainable per batch-2). Every review rubric states its purpose and threat model; findings outside them are out of scope. Stop-loss (round budget, v1.24, human ruling — Adjudication 4): every review has a budget of at most 10 rounds. A review reaching round 10 without acceptance triggers a kimi tie-break on one enumerated question — CONTINUE (further rounds are likely to reach acceptance on the existing findings) or STOP — with the review file's full round history inlined VERBATIM (summaries forbidden, per vacated batch 4) and the prompt committed pre-execution per the tie-break rules. On CONTINUE the budget extends to 15 rounds, an absolute ceiling; on STOP, or on exhausting round 15, the orchestrator decides against the north star (score advisory). Early exit retained from v1.23: ANY review at 3+ rounds with zero open high/criticals is decided by the orchestrator against the north star (score advisory). This supersedes v1.23's one-round cap for tooling-only changes. Budget scope for the canonical amendment topic (v1.25): plan/reviews/plan/amendment.md is a running log across amendment versions; the round budget counts the rounds spent on the amendment version currently under review, starting at 1 for each new version — the file's historical round total does not count against it. The 90-bar remains binding only for phase gates on the science.

Cross-model review, kimi (v1.6). kimi-k3 (`kimi-k3:cloud` via the local ollama daemon) is the second, independent reviewer: `python3 tools/run_kimi_review.py <phase> <topic> <threshold>` writes `plan/reviews/<phase>/<topic>-kimi.md` under the same round-log, append-only, and severity contracts, serialized on the same lock. Cadence: at least one kimi cross-review per phase on the gate-critical work, plus each retrospective (threshold 75 there). kimi is advisory — sol remains reviewer of record and kimi acceptance is not required for gates — but the orchestrator verifies kimi's high/critical claims and injects confirmed ones into sol's next round for adjudication; a confirmed, unrefuted kimi finding must be resolved like any other. Tie-break: when the orchestrator and sol deadlock on a finding after two full resolve-or-refute round trips, kimi receives the finding text VERBATIM, the fix or refutation evidence, and both arguments verbatim (summaries are forbidden — the vacated batch 4 shows why), and renders a verdict; the verdict is executed and ledger-recorded. Trigger order, reconciled (v1.22): two deadlocked round trips → kimi tie-break; sol disputing an EXECUTED tie-break in its next round → human touchpoint; a second dispute after a human ruling is out of scope for review. Mandatory human touchpoint (1) of the Autonomy policy now triggers only if sol's next round disputes the executed tie-break.

Review-session continuity (v1.6). One review (one phase/topic file) is served by ONE reviewer session across all of its rounds: round 1 records the codex thread id (plan/reviews/.sessions/, machine-local, gitignored) and every later round resumes it, so the reviewer keeps its original context and re-verifies its own findings against the diffs instead of re-litigating from scratch. Anti-churn rule, binding on reviewers: rounds after the first re-examine existing findings and the changes; new findings are added only for regressions introduced by fixes or clear in-scope misses from the original review — scope never expands round-over-round. A new review (next phase or topic) starts a fresh session and then holds it for its own rounds. If a stored session is unusable, the wrapper falls back to a fresh run carrying the prior review file, noted in the wrapper log; the orchestrator MUST append the continuity-loss note to plan/LEDGER.md in the same working session (v1.18 — the log alone is not the audit record). kimi is stateless; its continuity is the prior rounds inlined in each call plus the same anti-churn rule.

Phase retrospectives and agent evals (v1.6). After each phase's exit commit, before the next phase starts, the orchestrator writes `plan/retros/<phase>.md`: what went well and what went poorly, with evidence (finding counts and severities per round, fix attempts, reruns, wrapper failures, wall clock vs budget), root causes, and concrete optimizations. Every optimization lands as a diff in the retro commit — the AGENTS.md diff is quoted inside the retro document so the kimi retro review audits it (v1.19), an AGENTS.md entry (the agent playbook codex auto-loads and CLAUDE.md imports), a tooling or prompt fix under tools/, or a deferral ledgered with reason; changes to governed content still go through the amendment path. kimi reviews each retro (advisory, threshold 75) against one rubric question: does the retro assign blame where the evidence points. Performance is measured, not self-reported: `tools/agent_metrics.py` computes, from reviewer-authored review files and git history, first-round scores, rounds-to-acceptance, findings-per-round by severity, and open high/critical counts; the retro records the trend plus two hand-counted metrics, escaped defects (a finding whose root cause was accepted in an earlier phase) and lesson recurrence (a new finding matching an existing AGENTS.md lesson — the direct measure of whether the improvement loop works; target zero). Metrics are advisory and never gate science.

Autonomy policy (v1.5). The project runs autonomously by default; honesty is enforced by the adversarial review protocol above and by the deterministic proof tests, not by human checkpoints. Concretely: wherever this plan says an amendment or decision is "human-authorized," the autonomous path is that the orchestrator drafts the amendment with rationale, a sol@xhigh review of it is run (topic `amendment`, same wrapper), and it takes effect only once that review is accepted with zero open high/critical findings; the ledger records it and the human can audit asynchronously. Threshold freezes at first run launch remain absolute — no review can undo a freeze. Sequencing, auditable (v1.7, binding without exception since the v1.16 human ruling): an amendment's review must be accepted BEFORE the amendment commit lands — the reviewer reads the working-tree diff or draft, which the wrappers support (pre-existing dirty state is baseline, not drift); non-governed narrow commits (tie-break prompts, artifacts) go through `tools/commit_narrow.sh`, which stages only listed paths and refuses governed ones (v1.22, finding #12); amendment commits are made ONLY through `tools/amend.sh`, which takes the repo lock and refuses to commit unless the amendment review is ACCEPTED with its latest round quoting the current tree id from `tools/amend.sh --tree-id` (content binding: the reviewed tree IS the committed tree; any post-review edit changes the id and blocks the commit) and naming this version, the PLAN.md index line and plan/AMENDMENTS.md entry exist, and the topmost STATE line declares this amendment lands in this commit while naming the POST-commit next command (declared intent, v1.21 — committed STATE is fresh by construction) (v1.19, hardened v1.20 after the reviewer found the first version validated none of the review chain). Correction on the record (v1.20): Human Adjudication 2 made pre-commit review binding from that ruling forward; the orchestrator wrongly applied an extinguished initial-loop exception to v1.18 and v1.19 — both stand as committed, their substance reviewed post-hoc by rounds 16-17, and the violation is ledgered. Changes to acceptance tooling (check_review_scores.py, review_round_tracking.py, the wrappers), to reviewer/coder prompt fragments, or to AGENTS.md (behavioral instructions every agent loads; added v1.22 closing process#31) arising from retrospectives likewise take effect only after an amendment review accepts them (fragments added v1.13). Tie-break auditability (v1.13): every future tie-break's full prompt is committed verbatim to plan/tiebreaks/<phase>.md BEFORE the call executes. Ambiguities in this spec (old rule 7) are resolved autonomously by choosing the most conservative reading, recording the choice in the ledger, and flagging it for the next review round, rather than blocking on the human. The only mandatory human touchpoints are: (1) a review finding deadlocked after two full resolve-or-refute round trips, (2) a gate still red after three fix attempts (rule 4), (3) projected spend beyond 2x a phase budget, (4) renting external compute or any spending beyond this machine (Phase 7), and (5) anything destructive or outward-facing. Everything else proceeds without asking.
